## 轮次：修审核打回的两条（`no-unsupported-api` ×4 + `require-description` ×1）

### 报的是什么

| 审核报的 | 位置 |
| --- | --- |
| `Uses Obsidian APIs newer than the declared minAppVersion`（`obsidianmd/no-unsupported-api`）×4 | `src/core/secretStore.ts` 的 `secretStorage` / `getSecret` / `setSecret` |
| `Unexpected undescribed directive comment`（`eslint-comments/require-description`） | `src/core/themeName.ts:35` 的 `eslint-disable-next-line no-control-regex` |

### 最重要的一条教训：自查全过 ≠ 审核能过

`scripts/checks.mjs` 第 1 项**本来就在查「API 版本 vs minAppVersion」**，
第八节还写着「全部通过」。可它把 `SecretStorage.*` 放进了 `KNOWN_SAFE` 豁免表 ——
**恰好把审核要查的那几条放过去了**。

> **自己重写一遍判据，就会重写一遍它的盲区。**

这和第 2026-09-20 那轮的「工具写了、触发点没接上」是同型问题的另一种表现：
那次是「有工具没人跑」，这次是「有检查但判据不同」。

### 做法：不猜规则，装官方规则实跑

装了 `eslint-plugin-obsidianmd`（审核用的同一套），本地复现出**一模一样**的 6 条。
这一步值得单列：**「我以为审核要什么」和「审核实际要什么」是两件事**，
而前者在上一轮刚刚被证明不可靠。

### `requireApiVersion` 的写法要求（实测矩阵，别再猜）

| 写法 | 审核 |
| --- | --- |
| `if (requireApiVersion("1.11.4")) { …getSecret(id) }` | ✅ |
| `requireApiVersion("1.11.4") && …getSecret(id)` | ✅ |
| `requireApiVersion("1.11.4") ? …getSecret(id) : undefined` | ✅ |
| `if (!requireApiVersion("1.11.4")) return; …getSecret(id)` | ❌ |
| `requireApiVersion(SECRET_STORAGE_SINCE)`（常量） | ❌ |

规则只在成员访问**位于被守卫的分支内部**时才算数。**提前 return 型守卫**
（语义完全正确、也是最常见的写法）不被承认，因为成员访问是那个 `if` 的**兄弟语句**；
**版本号抽成常量**也不行，规则源码里判的是 `arguments[0].type === Literal`。

两条都特别自然，所以都在 `secretStore.ts` 文件头写死「别改回去」。

### 一次差点犯的错：用结构类型「骗过」规则

第一版把返回类型换成结构类型 `SecretStorageLike`，规则不报了。
**但变异测试立刻暴露问题：把守卫整段删掉，lint 依然全绿。**
也就是说「报不报」与守卫无关了 —— 那不是修好，是**把闸门拆了**。
最终改成「正向 `if` + 字面量」，让 lint 的绿/红**真的取决于守卫在不在**。

### 新增两道防线（各管一半，都要）

| 防线 | 管什么 |
| --- | --- |
| `pnpm lint:review`（接进 `build`） | 官方规则本体；守卫没了就红 |
| `tests/core/secretStore.test.ts` | **运行时**真不去碰（lint 证明不了这个） |

`lint:review` 只开审核打回过的两条、其余显式关闭：完整那套在本仓库有约 48 条
既有告警，全开会让闸门**从第一天起就是红的**，于是没人看 —— 那和没有闸门一样。

变异验证（两个方向都实跑）：
- 删掉守卫 → 6 条错误，闸门 exit 1；
- 版本号字面量换成常量 → 7 条错误，闸门 exit 1。

### 顺带查出的真 bug：清空令牌后诊断说「已就绪」

写运行时用例时发现两条分支**对同一个问题给出相反答案**：

- localStorage 分支：空串 → `undefined`；
- SecretStorage 分支：`value ?? undefined` → 返回 `""`。

而 `syncService.ts:552` 判的是 `getToken(...) !== undefined` ——
**用户清空令牌后，鉴权诊断会报「平台已就绪」**。已统一为「空串算没有」。

### 又一个被测试抓住的疏漏

第一版守卫写成 `if (requireApiVersion("1.11.4"))`，顺手把**对象存在性检查**丢了。
后果：版本够新但 `secretStorage` 缺失时，`?.` 把整次读写**静默吞掉** ——
令牌存不进去，且没有任何报错。

3 个测试文件、4 条用例立刻变红（`secretStore` / `hostRegistry` / `auth`）。
**是测试抓住的，不是人看出来的** —— 而这正是「新增的运行时用例」在同一天
就还上了本：它抓的不只是审核那件事，还有我自己刚引入的回归。

最终条件两个都要：`requireApiVersion("1.11.4") && this.app.secretStorage`。

### 收尾

- 验证：849 条测试全绿（原 845 + 新增 4）、`pnpm check` 六项、`lint:review`、
  `typecheck`、`pnpm build` 全部通过；
- 文档：README 中英同步补 `lint:review` 说明；HANDOVER 新增第九节；
- `checks.mjs` 里那三条 `KNOWN_SAFE` 的**理由已改写** —— 原文写的是
  「运行时 typeof 检查」，现在代码已经不是那个写法了，理由必须跟着改，
  否则豁免表会变成误导后人的地方。

## 轮次：第三条审核打回 —— 插件改名 `OBSync` → `SyncHub`

同一轮里审核又回了第三条，和前面两条性质不同：**代码没问题，名字有问题**。

> Plugin name must not include parts of the name "Obsidian"

### 先搞清楚"这条到底是谁发的"

第一反应是去翻官方 eslint 规则 —— **结果它不背这个锅**。
`eslint-plugin-obsidianmd` 的 `validateManifest.ts` 里，禁用词只有
`["obsidian", "plugin"]` 两个字面子串。我把这段原逻辑套到自己的 manifest 上：

| 字段 | 结果 |
| --- | --- |
| `id` = `ob-sync` | 通过 |
| `name` = `OBSync` | **通过**（不含 `obsidian`） |
| `description` | 命中 `plugin` |

所以 `OBSync` 按公开规则**本该过**，报错来自审核门户自己那套更严的匹配器
（源码没公开，`obsidianmd/eslint-plugin`、`obsidian-releases`、官方文档仓库、
论坛我都翻过）。**判断依据**是 Developer policies 的商标条款：
"Don't use the 'Obsidian' trademark in a way that could confuse users into thinking
your plugin is a first-party creation."

### 用线上数据反推匹配规则

规则源码拿不到，就用 7884 个已上架插件当样本反推：

| 名字 | 含什么 | 在架 |
| --- | --- | --- |
| `OBSync`（我们） | **全大写 `OBS`** | ❌ |
| `WeChat Obsync` / `Tree Obs` / `Source Observer` | 词首大写 `Obs` | ✅ |
| `GitHobs` | 小写 `obs` | ✅ |
| `ObShare` / `ObDrawIO` | `Ob` + 大写 | ✅ |
| `Ostracon OB` | 全大写 `OB`（2 字母、词尾） | ✅ |

**在架的显示名里，一个含全大写 `OBS` 的都没有**；`Obs`/`obs`/`Ob` 却大量存在。
⇒ 它认的是"全大写三字母 `OBS`"这个缩写片段，**不是朴素子串**（否则 `Obsync` 也该挂）。

**反过来的强证据**：目录里本就有一批 **id 含 `obsync`** 的插件
（`obsync-ptop` / `obsync-webdav-gpg` / `obsync-private-sync` / `obsyncer`），
但它们的**显示名**一律不含 —— 说明卡的是显示名，`id` 不受影响。

### 我的一个失误

**推荐 `VaultSync` 之前没查重**，结果它已被占用（`vault-sync`，作者 thewordisbird）。
用户提出 `SyncHub` 后才去查 —— 这次学乖了，先查重再下结论：
无同名、无 id 冲突，且 `synchub` 里没有 `ob`/`obs` 序列（结尾是 `ub`）。
顺带查到 `vault+sync` 命名区已挤了 24 个名字，往那边取名本来就不划算。

> 教训：**"这名字不错"和"这名字能用"是两件事。** 建议一个名字之前，
> 先花一次 API 调用查重 —— 成本极低，而我跳过了它。

### 改名执行

284 处、36 个文件。**没有用全局无脑替换**：

- 只替换**大小写敏感**的 `OBSync`，所以小写 `obsync-` 内部前缀天然不受影响；
- 排除构建产物（会重新生成）与**按日期归档的工作日志**（那是历史记录，
  改了等于篡改当时发生的事）。

三层区分（已写进 `MEMORY.md` 当长期约定）：

| 层 | 值 | 处置 |
| --- | --- | --- |
| 显示名（manifest / 状态栏 / 命令名 / i18n / README / CHANGELOG） | `SyncHub` | 改 |
| 自我更新仓库坐标（`selfUpdate.ts` 的 `repo`、发布脚本、占位符 URL） | `SyncHub` | 改 |
| 插件 id（manifest `id`、安装目录） | `ob-sync` | **不改** |
| 内部前缀（CSS 类 / 视图类型 / 密钥 id） | `obsync-` | **不改** |

### 顺手抓到的两处（都不在审核清单里）

1. **`scripts/gitee-release.mjs` 写死了仓库名** `sofqi/OBSync` ——
   仓库一改名，`pnpm gitee:release` 就会打到旧路径。**这条最险**：
   它只在真发版那一刻才炸，平时完全看不出来。
2. **`MEMORY.md` 的 id 是过期的**（写着 `obsync`，而 0.1.4 起已是 `ob-sync`）。
   一份"长期约定"文档里躺着过期事实，正是最容易被当真、也最容易误导人的东西。

### 核实过但**不是**问题的

`description` 含 "plugin"（`community plugins`）。官方那条公开规则确实会命中它，
我一度准备改文案 —— 但查了线上数据：**7884 个里 5362 个** description 含 "plugin"、
**5348 个**含 "obsidian"。规则实际并未执行。**不改** —— 为一个不存在的告警把文案改别扭，
是把审核的判据当成了教条。

> 这条和本轮的 `OBS` 是同一套方法：**先去线上样本里验证判据是否真的被执行**，
> 再决定改不改。两次都靠它省掉了无谓的改动。

### 收尾

- 验证：849 条测试全绿、`checks` / `lint:review` / `typecheck` / `build` /

## 轮次：仓库改名完成核实 + id 也统一为 `synchub`

用户说「改好了」，让我核对并重新部署。核对顺带发现仓库改名**已经生效**：

| 检查 | 结果 |
| --- | --- |
| GitHub `Dyse-Sofqi/SyncHub` | ✅ 存在 |
| 旧地址 `Dyse-Sofqi/OBSync` | ✅ **自动重定向**到 `SyncHub` |
| Gitee `sofqi/SyncHub` | ✅ 存在 |

旧地址重定向这一点值得记下：它意味着**已装用户的自我更新不会断**，
所以"仓库改名"这件事的风险比我原先提示的低。

随后用户要求「id 改成 synchub 吧，统一一下」。

### 先摆清楚：这不是审核要求的

上一轮已经用线上数据证明**商标规则只管显示名、不管 id**（`obsync-ptop`、
`obsync-webdav-gpg` 等一大批 id 含 `obsync` 照旧在架）。所以这次改动**纯粹是
"统一"**，不是过审必需。

但我的判断是**该改，而且现在最便宜**：插件还没上架（0.1.4 被打回），
全世界的安装只有用户自己的两个库 —— 改 id 只需迁移这两处；
等上架之后再改，代价就是所有用户的数据。这个理由我写进了 CHANGELOG。

> 与上一轮"不为了不存在的告警改文案"并不矛盾：那次是**没有收益**的改动，
> 这次是**收益明确（一致性）+ 成本此刻最低**。判据不同，结论自然不同。

### 三层里只有 id 跟着动

| 层 | 处置 |
| --- | --- |
| 显示名 → `SyncHub` | 上一轮已改 |
| **插件 id：`ob-sync` → `synchub`** | **本轮改**（59 处 / 20 文件） |
| 内部前缀 `obsync-`（CSS / 视图类型 / 密钥 id） | **仍然一律不动** |

内部前缀不动的理由这轮体现得很直接：**`obsync-token-*` 与插件 id 无关**，
所以用户已存进系统密钥库的访问令牌**照旧可用** —— 改 id 没有连带作废凭据。
脚本里专门加了一段"内部前缀完整性检查"来守这条。

### 迁移（这轮真正的风险点）

Obsidian 按 id 找插件，于是：

- 安装目录 `plugins/ob-sync/` → `plugins/synchub/`；
- **`data.json` 不会自动跟着走** —— 不迁移就是静默丢配置（3 + 7 条跟踪项 + 全部设置）。

处理顺序（**先确认 Obsidian 已退出**，再动目录）：

1. `pnpm build:both` 部署到新的 `synchub/` 目录（非破坏性，不动旧目录）；
2. 把旧目录的 `data.json` 复制过去，**sha256 逐一比对**；
3. 用户关闭 Obsidian 后，再比对一次（怕退出时又写过），然后删掉旧目录。

结果：两个库都只剩 `synchub/`，跟踪项 3 / 7 条完好，旧目录已清。
**没有出现"插件列表里两个 SyncHub"** —— 那正是 0.1.4 改 id 时踩过的坑
（CHANGELOG 里写着"旧目录要手动删掉，否则会出现两个"）。

### 一个必须说清的后果

**跨 id 这一跳不能靠自我更新**：旧安装的 `SELF_PLUGIN_ID` 是 `ob-sync`，
而远端 manifest 的 id 已是 `synchub` —— 守卫会**拒绝写盘**。
那道守卫的职责正是"远端 id 不是我就不写"，所以它在这里"正确地帮了倒忙"。
已写进 CHANGELOG 与 HANDOVER：跨 id 必须手动重装一次，之后恢复正常。

### 顺手发现的一个真 bug（**未改**，留给用户定）

`en` 的 `.gitignore` 模板比 `zh-cn` **少一条**：`zh-cn` 有
`.obsidian/plugins/synchub/data.json`（本插件设置按设备、不该同步），
`en` **根本没有这一条**。

i18n 的编译期检查只管**键结构**、不管**字符串内容** —— 所以这条漂移一直没人发现。
后果是真的：英文用户的 `.gitignore` 不排除插件自己的 `data.json`，
设置会被同步，正是该模板注释里警告的"两台设备互相覆盖设置"。

没顺手改的理由：它会改变英文用户初始化仓库时写入的文件内容，属于 i18n 内容变更，
且与本轮"改 id"是两件事。已记入 HANDOVER 第十节「待办」。

### 收尾

- 验证：849 条测试全绿、`checks` / `lint:review` / `typecheck` / `build:both` 全过；
  两个库部署件 sha256 与本地构建逐一一致，`main.js` 中 `ob-sync` = **0** 处；
- 文档：CHANGELOG「未发布」补 id 条目（含升级注意与自我更新后果）、
  HANDOVER 第十节补「id 为什么又改了一次」、MEMORY.md 更新三层表与 id 历史；
- **仍未做**：版本号还是 `0.1.4`，没升版。

用户把令牌**明文贴在聊天里**了。处置：

这正合 RELEASE.md 的硬规矩（"令牌只从环境变量读，不写进任何文件、不写进 remote URL"），
而且这个项目自己论证过"别把凭据写进 remote URL"（`git remote -v` 一眼可见）。

### 补 en 的 .gitignore 模板

给 `en.ts` 的 `gitignoreTemplate` 补上本插件自己的 `data.json` 排除项，
与 `zh-cn` 对齐。中英模板现在一致。

### 顺手发现：remote 还指着旧仓库名

`git remote -v` 显示 origin/gitee 仍是 `.../OBSync.git`。虽然 GitHub/Gitee 都会重定向，
但依赖重定向是隐患（重定向哪天失效就静默失败），已改成 `SyncHub.git`。

### 发版流程（照 RELEASE.md 走，含三处"实测踩过"的坑）

| 步骤 | 结果 |
| --- | --- |
| 版本号三处同步 | `manifest.json` / `package.json` / `versions.json` → `0.1.5` |
| CHANGELOG | 「未发布」落成 `[0.1.5] — 2026-09-21` + 链接定义 |
| 发版前验证 | check 六项 / lint:review / typecheck / **849 测试** / build / verify:mobile 全过 |
| 提交 | `6379422`（54 文件） |
| 推送 | `git push` —— pre-push hook 自动跑了 `verify:head`，**HEAD 上 849 条全过** |

| Gitee 镜像 Release | 3 个附件，**下载回来比对 sha256 也一致** |
| 两个库部署 | 都到 `0.1.5`，产物与发布件 sha256 一致，跟踪项 3/7 完好 |

### 这轮踩到的坑

**1. `git push` 报 `getaddrinfo() thread failed to start`（两次）**

看着像网络问题，但 `git ls-remote` 同一时刻**正常**。第三次重试就过了 ——
属于**间歇性资源竞争**，不是配置问题。

> 教训：git 的网络错误要**先用 `ls-remote` 对照**再下结论。`ls-remote` 通而 push 不通，
> 基本可以排除"网断了/凭据错了"，直接重试比改配置有效。

**2. 提交信息里的 `->` 被 PowerShell 当成重定向**

`git commit -m "...OBSync -> SyncHub..."` 直接报 `unknown switch '>'`。
改用 `git commit -F <文件>`（消息写进 UTF-8 文件）解决。

> 这已是本机 PowerShell 第三次咬人（前两次：`Set-Content` 把中文写成乱码、
> 不支持三元 `? :`）。**凡是要给 git/外部程序传多行或含特殊符号的中文，
> 一律走文件或 Node，不要走 PowerShell 的引号。**

**3. `gh api --jq '...'` 被 PowerShell 拆成多个参数**

报 `accepts 1 arg(s), received 2/3`。改用**管道 + `ConvertFrom-Json`** 在 PowerShell 里解析。

**4. Gitee release 的 `assets=5` 一度以为传多了**

### 是的，是我的纰漏

上一轮用户要求"id 改成 synchub 统一一下"，我做了查重、也核对了目录，然后判断
"**插件还没进目录 → 改 id 现在最便宜**"。

**我核对错了对象。** 决定 id 的是**审核系统的提交记录**，不是已发布目录：

| 我查的 | 实际决定 id 的 |
| --- | --- |
| `community-plugins.json`（已发布目录）—— 查不到 `ob-sync` | **审核系统的提交记录** —— 0.1.4 那次提交已登记 `ob-sync` |

提交记录是**独立且长期存在**的状态，跨多次打回一直保留。**"没进目录"不等于"没有既有身份"。**

更糟的是我还在 CHANGELOG / HANDOVER 里写了"**这不是审核要求的**" ——
就商标规则而言没错，但我因此**放松了对这次改动的警惕**，没有去问"id 还有别的绑定吗"。

> 已把这条写进 `MEMORY.md` 当长期规矩：
> **与插件身份相关的字段（id），在被明确要求之前不要动。**
> 想核实也只能靠审核报错 —— 本地查不到。

脚本里加了"保留项自检"三条：显示名 / 仓库坐标 / Gitee 仓库名必须仍是 `SyncHub`。

**最终形态：显示名 `SyncHub` + id `ob-sync`，两者不一致是刻意的** ——
审核登记决定 id，商标规则决定显示名，来源不同，不必也不该统一。

CHANGELOG 与按日期归档的工作日志**不动** —— 那里记的是"当时确实改成过 synchub"，
是历史事实；0.1.6 的条目说明回退原因。
