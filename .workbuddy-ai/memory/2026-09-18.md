## 轮次：上一轮我自己写的那条继承规则，有一半是错的

上一轮给 `recordItem` 加了「继承上一次的 `origin`」，理由是更新路径手里没有源地址。
这一轮回头验它 —— **发现它在一种情况下会显示一个错的地址**。

### 问题

身份是 `(kind, id)`，所以「**同一个插件换个仓库装**」会落在**同一条记录**上
（上游 ↔ 自己的 fork 之间切换，这是真会发生的事）。而 `origin` 说的是**上一个**
仓库的地址。无条件继承的话：

1. 从镜像装 `owner/demo` → 记录 `{ host: gitee, origin: github/owner/demo }`
2. 改用 `other/demo`（同一个 manifest id）装 → 这次没有镜像，手里没有 origin
3. 无条件继承 → 记录变成 `{ host: github, owner: other, origin: github/owner/demo }`
4. **列表第一行显示 `owner/demo`，而插件实际来自 `other/demo`**

偏偏用户看那一行，就是想知道「这个插件到底跟谁走」。先写了失败用例钉住症状
（`expected {...} to be undefined`），再修。

### 修法：只在**来源没变**时继承

```ts
const previousRef = previous ? itemRepoRef(previous) : undefined;
const inheritedOrigin =
    previousRef && isSameRepo(input.repoRef, previousRef) ? previous.origin : undefined;
const origin = input.origin ?? inheritedOrigin;
```

与 `frozen` 的继承正好形成对照（已写进注释）：冻结是**这个已安装的东西**的属性，
换个仓库装仍然成立；`origin` 是关于**仓库**的，仓库换了就不成立。
顺带核对过其余几个字段：`channel` / `installedVersion` 每次都取新值，
`requestedVersion` 有自己的默认值，都不该继承 —— 只有 `origin` 需要这条规则。

### 变异验证（三个方向）

- **退回「无条件继承」**（= 上一轮我写的那版）→ 新用例失败。**这条同时证明 bug 是真的**；
- **干脆不继承** → 「更新时源地址被继承」那条失败；
- **拿上一次的源地址去比**（`isSameRepo(input.repoRef, previous.origin)`，比错对象）→
  同一条失败（更新场景里 input 是镜像、origin 是源仓库，永远比不相等）。

### 记一条方法上的事

**这一轮的 bug 是我上一轮引入的**，而且是上一轮那六条变异全都抓不到的那一类 ——
因为我当时只验了「记不记」「继不继承」，没验「继承的条件对不对」。
**变异验证只能覆盖你想得到的失败方式**；隔一轮回头重读自己刚写的那段，
比在同一轮里加更多变异更有用。

验证：`pnpm check` 6 项全通过；`pnpm test` **612 项全绿**（46 个文件）；`pnpm build` 通过并部署。

未提交 —— 与上一轮同样的理由：改动落在另一批进行中工作的同一批文件里，按文件分不开。

## 轮次：主题的身份键漏了「大小写不敏感」

上一轮是回头看自己改的东西。这一轮回到「同一个概念写了几份、判据一不一致」这条
老矿脉 —— 它在「有哪些平台」那次挖出过真 bug（`settings` 那份副本漏一个平台，
用户在**那个平台**上装的插件会被无声丢弃）。这次落在**主题的身份**上。

### 先确认这条规则在别处是怎么写的

主题没有 id 字段，身份就是 `themes/` 下的**目录名**。而 macOS / Windows 的文件系统
不区分大小写，所以代码里三处都按「大小写不同 = 同一个主题」办：

```
themeFolder.ts:64    resolveThemeFolder    → 精确命中，再兜一次小写
existingThemes.ts:86 listInstalledThemes   → 按 toLowerCase 去重
installerService:431 getActiveTheme 比对   → 两边都 toLowerCase
```

第四处是身份键 `availableUpdateKey`（`<kind>:<id>`）—— 它是**精确比较**。
而它是 `sanitizeTrackedItems` 去重、`availableUpdates` 剪枝、`BindExistingModal`
的「已跟踪」过滤、`TrackedItemsList` 取徽标**全都用**的那个键。
`addTracked` 还自己就地写了一遍同样的精确比较，等于同一个判据两处各写一份。

### 后果不是「多一行」

同一个主题能有两条记录，而 `resolveThemeFolder` 会把它们解析到**同一个目录** ——
更新其中一个等于更新两个。徽标的键是 `<kind>:<id>`：`theme:Minimal` 与
`theme:minimal` 是两条不同记录，检查完只有一条会亮。用户看着列表里两行一模一样的
主题，分不出哪一行是真的，也说不清为什么其中一个「更新」没反应。

触发路径也真实：`data.json` 是**随笔记仓库同步到多设备**的（项目刻意这么设计），
一台机器上目录叫 `Minimal`、另一台叫 `minimal` 完全可能。

### 修法

`availableUpdateKey` 里按 kind 归一，**只归一主题**：

```ts
const id = item.kind === "theme" ? item.id.toLowerCase() : item.id;
return `${item.kind}:${id}`;
```

插件侧**刻意不归一**（与 `pluginId.ts` / `themeName.ts` 那对判据同一个道理）：
`manifest.id` 有 `/^[a-z0-9-]+$/`，本来就不可能有大写；把两边并成一个
`toLowerCase()` 看着像简化，实际是把插件侧「id 不同就是不同对象」的语义也改了。
`addTracked` 改成用这个键判重（不再就地写比较）。

### 迁移代价：零

改键格式理论上会让已持久化的 `availableUpdates` 里旧格式的主题键被
`sanitizeAvailableUpdates` 剪掉一次（徽标丢到下次检查为止）。但主题是**尚未提交的
新功能**，没有已装机用户 —— 所以现在改是最便宜的时候，再晚就得写迁移。

### 测试与变异

- `themeService.test.ts` +1（写入侧：绑 `Minimal` 再绑 `minimal` → 只留一条）；
- `settings.test.ts` +3（读取侧同样一条；外加身份键的两条，钉住「只归一主题、
  插件原样保留」这条**刻意的不对称**）。

**四个方向的变异**全部被抓住：键退回精确比较 → 3 条失败；
键修好但 `addTracked` 写回就地比较 → 1 条；
「合并简化」（插件也归一）→ 1 条；反过来（只归一插件）→ 3 条。

### 顺手核对、确认没问题的几处

- `installFiles.ts`（`pluginFiles.ts` 改名 + 参数化）**保住了**我两轮前修的那条
  `assetUnreachable: !(err instanceof NotFoundError)` 与「传输层失败后不再试资产」的短路；
- 改名后的测试文件**没丢用例**（旧的 11 条全在，另加 5 条主题的）；
- 其余按 id 精确比较的地方（`unbind` / `setFrozen` / `recordItem` 的查找）传进去的
  都是记录里那个 id，与记录本身必然相等，不受影响；
- `communityIndex` / `communityPlugins` / `communityThemes` 是真的抽了公共骨架，
  没有分叉。

验证：`pnpm check` 6 项全通过；`pnpm test` **616 项全绿**（46 个文件）；`pnpm build` 通过并部署。
仍未提交（与前两轮同样的理由）。
