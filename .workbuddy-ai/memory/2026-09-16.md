## OBSync 项目启动（阶段一完成）

**目标**：单个 Obsidian 插件，合并两个能力 —— 笔记仓库同步（复刻 `obsidian-git`）+ 社区插件安装（复刻 `obsidian42-brat`），并从「仅 GitHub + 英文」扩展到「GitHub / Gitee 双平台 + 中文优先」。

参考项目在本机的位置：
- `F:\_Workspace\GitHub-Project\obsidian-git`（~16.9k 行 TS）
- `F:\_Workspace\GitHub-Project\obsidian42-brat`（~5k 行 TS）

### 已确认的四项决策
仅桌面（不做 isomorphic-git） / 分阶段逐段验收 / id = `obsync` / 加做 GitHub→Gitee 镜像自动发现。

### 阶段一产出
- 脚手架：TS + esbuild（构建即部署到测试库）+ vitest + pnpm。
- `core/`：i18n（中文为规范源）、settings（递归合并默认值，新增设置项免写迁移）、secretStore（SecretStorage 优先 / localStorage 回退）、logger、notice（错误类型 → 用户可读文案）。
- `host/`：`IRepoHost` 接口 + `GitHubHost` + `GiteeHost` + `repoRef` 解析器 + `http` 封装 + `statusMapper`。
- 文档：`docs/reference-analysis.md`（两个参考项目的分析）、`docs/PLAN.md`（复刻规划与阶段划分）。

### 实测发现（读文档看不出来，都是打真实接口才发现的）
1. **Gitee releases 默认升序**。不传 `direction` 时 `mindspore/mindspore` 首个返回 `v0.1.0-alpha`(2020)，传 `direction=desc` 才是 `v2.7.2`(2026)。直接照搬 BRAT 的 GitHub 逻辑会静默安装六年前的版本。
2. **Gitee 的 API raw 端点对匿名请求返回 401**（"登录失效，无权限访问该资源"），**即使公开仓库也如此**。匿名读文件必须走网页通道 `https://gitee.com/{o}/{r}/raw/{ref}/{path}`（302 → raw.giteeusercontent.com）。代价是必须显式给出 ref。
3. **Gitee 的 `html_url` 带 `.git` 后缀**，GitHub 不带。
4. Gitee 鉴权走 `access_token` **查询参数**，GitHub 走 `Authorization` 请求头 —— 这个差异无法用统一装饰器消除。
5. Obsidian `requestUrl` 的 `throw` 选项**默认 true**（400+ 直接抛异常），要自己处理状态码必须显式传 `throw: false`。
6. Gitee 的 `/v5/search/repositories` 匿名调用返回空数组，搜索功能在 Gitee 侧不可用。

### 验证
- `pnpm test`：78 项单测通过。
- `pnpm test:live`：11 项真实 API 测试通过（含一条对照实验，实证 Gitee 默认升序）。
- `pnpm build`：产物 35KB，仅 `obsidian` 一个外部依赖，无 node 内置模块被打包。

### 顺带发现
测试库里已装的第三方插件 `gitee-sync-plus` **不是真 git 实现** —— 只调 `api/v5` + `access_token` 做文件级收发，没有提交历史、分支、冲突处理。所以走真 git 是差异化，不是重复劳动。

### 下一步（阶段二）

## 验收复查（墨回来接手）：修 2 个真 bug + 补 3 处降级 + 补回 1 个漏做的功能

用户把项目交给 ZCode 跑完阶段二、三后，让我独立验收。做法是**不看实现者的结论，
只跑验证 + 读代码**。结论：架构与文档质量确实好（无 `as any`、无 ts-ignore、
无 console 泄漏、无 TODO），但**测试套件实际是红的**（10 个失败），
而且有几处「文档说做了、实际没生效」。

### 真 bug

1. **`unstage` 的「HEAD 未出生」回退从未触发**。正则写的是
   `/could not resolve HEAD/`，而 git 实际输出是 `fatal: could not resolve 'HEAD'`
   —— **带单引号**。回退分支形同虚设，症状是「全新仓库里取消暂存直接报错」。
   HANDOVER 第六节第 4 条还写着"unstage 已做回退"，属于文档比实现乐观。
   教训：**靠 git 的错误文案做分支判断，正则必须用真实输出校准**，
   不能凭记忆写（我记忆里也是"没引号的版本"）。

2. **`registerView` 用了 `this.sync!` 且无平台守卫**。`createSyncModule` 在移动端
   返回 undefined，视图工厂会解引用它。命令入口有守卫，但视图类型一旦注册，
   恢复工作区布局时仍可能被实例化。

### 真缺口（都影响用户，不是洁癖）

3. **release 资产下载失败 = 整个安装失败**。同一个文件在源码通道现成可取，
   却因为资产 CDN 抖动而整体失败。实测资产地址（`github.com/.../releases/download/`
   → `objects.githubusercontent.com`）**3 次里 2 次 21 秒超时 0 字节**，
   而 `api.github.com` / `raw.githubusercontent.com` 稳定。
   → `loadReleaseFile`：资产下载**失败**（不只是"不存在"）也回退该 tag 的源码。

4. **GitHub 的 raw 域名不可达时没有退路**。国内 `raw.githubusercontent.com` 常被阻断
   而 `api.github.com` 可达，两者可达性互不相关。Gitee 侧早就有 API↔网页 的双通道，
   GitHub 侧只有一条路。→ `readFile` 回退 contents API。

5. **`fileWebUrl` / `commitWebUrl` 是死代码**。阶段一就把这两个跨平台 URL 构造器
   写好了（还从 hostRegistry 转出），但没有任何地方用 ——
   也就是 PLAN 里规划的「在浏览器打开文件/历史」（`openInGitHub` 的 provider 化）
   根本没接上。→ 新增 `features/sync/remoteLinks.ts` + 2 条命令 + 文件右键菜单。
   两个平台网页路径格式一致，所以**没有平台分支**。

### 测试质量

6. **live 测试长期飘红**：Gitee 匿名 API 限流导致 4 个用例失败，文档的说法是
   "等窗口重置再跑"。但**预期会红的套件比跳过更糟** —— 它会训练人忽略失败，
   真有回归时也看不出来。→ 限流时跳过并打印可行动提示（配 `OBSYNC_GITEE_TOKEN`）；
   配了令牌还被限流才真失败。走网页 raw 通道的用例**不**包装（那条不吃 API 配额）。
7. **9 个 git 用例超时**：根因是本机**进程创建约 340ms**（连 `cmd /c echo` 也要 317ms，
   不是 git 特有的）。`makeCluster()` 一个用例起十几次 git 就要 4~5 秒，
   vitest 默认 5 秒必然不够。→ `testTimeout: 30_000`，清理加 `maxRetries`（Windows EBUSY）。
   **`simpleGitManager.test.ts` 单独跑约 150 秒** —— 文档早先写的"整个套件 ~1.5s"是错的。

### 顺带验证到的

- **`http.extraheader` 的客户端侧行为已实证**：用本地 HTTP 服务器验证 git 在
  **第一个请求**（`/info/refs?service=git-upload-pack`）就带上 `Authorization: Basic`，
  不等 401 挑战；再用「让 git 在同一次调用里读回 `-c` 配置」验证 simple-git 的
  `config` → `-c` 传递。剩下未验证的只有 **Gitee 服务端是否接受令牌当密码**。
- **simple-git 3.36 起会守卫 `.env()` 传入的环境变量**：本机有 `GIT_PAGER=cat`，
  传 `{...process.env}` 会直接抛 `Use of "GIT_PAGER" is not permitted without
  enabling allowUnsafePager`。表现为「本地服务器收到 0 个请求」，看着像网络问题。
  生产代码不调 `.env()`，不受影响 —— 这是测试写法的坑。

## 验收复查续：i18n 缺口（同日晚）

上一轮修完逻辑层后，继续查 UI 层与 i18n。**发现一个系统性缺口**：

### 问题
i18n 的编译期保证只能覆盖「locale 文件之间的结构一致」，
**管不住「代码里直接写了一句中文」**。而错误路径恰恰最容易这么写 ——
因为抛出点（`manifest.ts` / `pluginFiles.ts` / `pluginFolder.ts` /
`simpleGitManager.ts`）都是**纯逻辑，拿不到 `t`**。

写了个扫描脚本（`.probe/check_hardcoded_cjk.py`）一量：**26 处**硬编码中文。
其中 22 处是用户可见的错误文案 —— 也就是**英文界面下会冒出中文错误**。

佐证：i18n 里有 **7 个键写了却从未被引用**
（`gitNotFound` / `missingManifest` / `missingMainJs` / `noReleaseFallback` /
`sourceRelease` / `sourceRaw` / `installing`）—— 正是「本来打算本地化但没接上」的证据。

### 修法
沿用本轮为 sync 建立、并已验证的模式：

| 层 | 职责 |
| --- | --- |
| 逻辑层 | 抛 `InstallerError({ kind, ...params })`；`message` 只放**技术性描述**（英文，进日志） |
| 注册 | `createXxxModule()` 里 `notifier.registerErrorTranslator(...)` |
| 展示层 | `Notifier.describeError()` 按类型码取 locale 文案 |

关键设计：**可辨识联合 + `switch` 穷尽检查**。新增类型码却忘了加文案，
`const exhaustive: never = detail` 会**编译报错** —— 漏翻译不会留到运行时。
`Notifier` 用**注册制**而非 `import` 各功能的错误类型，`core/` 保持对 `features/` 无知。

顺带发现**两处错误类型用错**：「没有上游分支」「游离 HEAD」都抛了 `GitNotRepoError`，
提示语是「请先初始化仓库」—— 让用户去初始化一个已存在的仓库，**指错方向**。
新增 `NoUpstreamError` / `DetachedHeadError`。
（教训：**错误类型用错比没有类型更糟**。）

  语言下拉的「简体中文」标签（本就该用母语写）、`giteeHost` 的三个限流**检测词**。
- 测试约定改为**断言类型码，不断言消息文本**（文案来自 locale，改文案不该让测试变红），

## 自动定时器的两个真 bug（同日晚）

继续查定时器 / 串行队列 / 视图生命周期 —— 这几类最容易出隐蔽 bug。在
`automatics.ts` 里发现两个，都是"读代码不容易看出来"的那种：

### 1. 时间戳没按库隔离
用原生 `globalThis.localStorage` 存「上次执行时间」，而那是**所有库共用的存储区**。
于是 A 库刚自动提交过，会让 B 库刚打开就立刻提交一次；两个库的自动周期互相干扰。

**对照参考项目确认过**：obsidian-git 用的是 `app.saveLocalStorage` / `loadLocalStorage`
（按库 API），而且专门写了一段迁移把老数据从原生 localStorage 搬过来 ——
说明这是个它已经修过的问题。OBSync 漏了这一条。
→ 改走 `app.saveLocalStorage` / `app.loadLocalStorage`。

### 2. `stop()` 挡不住 in-flight 的 `fire()` 重新起表
`fire()` 是异步的，跑完会重新起表。若这期间 `stop()` 被调用过（插件卸载、
设置变更触发的 `restart()`），那个 in-flight 的 `fire()` 回来照样起表：
- `stop()` 之后仍有定时器在跑；
- **更糟**：`restart()` 已经起过一个，新起的会把 `Map` 里的记录**覆盖掉**，
  先前那个**再也 clear 不掉** → 同一动作每个周期跑两次。

→ 引入世代计数器：`stop()` 自增，`fire()` 开始时捕获、回来时若已变则放弃起表。

### 验证：两次变异验证
计时类代码"看起来对"很容易，所以两个修复都做了变异验证：
- 去掉世代守卫 → 两条竞态用例失败（`stop()` 后仍在跑，得到 4 次调用而非 1 次；
  `restart()` 场景 3 次而非 2 次，**正是预测的重复触发**）
- 改回全局 localStorage → 两条存储用例失败

新增 `automatics.test.ts`（8 项，用 `vi.useFakeTimers()`）。
其中一条精确断言了「启动时剩 20 秒 → 恰好在启动后 20 秒触发」，
同时证明了「按剩余时间起表」而不是「重新计满」。

## syncService 里的三个问题（同日晚）

接着查串行队列与编排。发现一个**数据完整性 bug** 和两个语义错误。

### 1. 冲突未解决时「提交全部」会把冲突标记提交进历史（真 bug）
冲突文件在 `git status` 里是 `UU`，于是 `mapStatus` 把它**同时**归进 `staged`
（index 位非空）与 `unstaged`（worktree 位非空）。结果是 `doCommitAll` 里那个

```ts
if (dirty === 0 && status.conflicted.length === 0) return { kind: "nothing-to-commit" };
```

在有冲突时**必然放行** —— 继续 `git add -A` + 提交，把 `<<<<<<<` / `>>>>>>>`
当普通内容写进历史。而本模块的设计文档明说这是要避免的事。

**触发路径很现实**：上次同步遇到冲突没处理 → 自动提交定时器到点 → `sync()`
第一步就是 `doCommitAll()`。

→ `doCommitAll` 开头显式拦冲突并抛 `ConflictError`（复用已有的错误类型与文案链路）。
变异验证：去掉守卫后用例报 `promise resolved "{ kind: 'committed' }"`，
也就是**它真的提交了**。

### 2. `isBusy` 的语义错了
```ts
this.running = true;
return task.finally(() => { this.running = false; });
```
布尔量在**第一个任务 settle 时**就置 false，而此时队列里第二个任务还在跑 ——
于是「忙」在真正有活干时报"空闲"。automatics 靠它决定"跳过本轮"，
状态栏也靠它显示忙碌状态，语义错了会连锁出错。
→ 改用计数器（排队中 + 执行中）。

### 3. `sync()` 整条链路都显示「正在提交」
只在开头 `setActivity("committing")` 一次，拉取与推送阶段状态栏显示的是错的。
→ 按阶段更新。

新增 5 项用例（含变异验证）。`syncService.test.ts` 从 7 项增到 12 项。

### 方法论小结（这轮反复用到）
**变异验证是唯一靠得住的确认方式**。计时/并发/守卫类代码"看起来对"太容易，
每个修复都注入回原 bug 确认用例变红 —— 这轮三次变异都观察到了预期的具体现象
（调用次数翻倍、`resolved` 而非 `rejected`、存储位置不对），而不是笼统的"失败了"。

## 视图层的两个问题（同日晚）

### 1. 点按钮失败时界面毫无反应（真 bug）
`SourceControlView.run()` 的 catch 写着「通知已由 service/notifier 完成」，
但那只对两种情况成立：拉取冲突（`doPull` 里处理）与没有远端（`doPush` 里处理）。
其余错误 —— **推送被拒、鉴权失败、找不到 git、网络问题** —— 会原样上抛，
然后被**静默吞掉**。症状：用户在视图里点「推送」，远端拒绝了，界面上什么都不发生。
→ catch 里调 `notifier.reportError(err)`。

（命令入口 `main.ts` 的 `runSyncAction` 是对的，只有视图这条路漏了。
教训：**同一件事有多个入口时，错误处理容易只做对一处**。）

### 2. 冲突文件在变更列表里显示三次
又是那个 `UU` 根因：冲突文件同时进 `staged` 与 `unstaged`，
列表再单独渲染一轮 `conflicted`，于是一个冲突出现三次。
→ 抽出 `visibleChanges()` 过滤掉 `conflicted` 状态，并加 4 项测试。
（抽成纯函数而不是做 DOM 级测试 —— 视图的 DOM 测试性价比太低。）

### 顺带排查
grep 了所有 UI 文件的裸 `catch {}`，只剩 `safeListBranches`（列分支失败返回空数组，
是有意为之），没有同类问题。

## 「编辑远端」的校验过严（同日晚）

`EditRemoteModal` 用 `tryParseRepoRef` 做校验，等于**只接受 GitHub / Gitee 地址**。
但**同步本身是纯 git 操作** —— 自建 GitLab、内网 git 服务器、本地裸仓库、
`file://` 路径都能同步。被拒的理由说不通，而提示语只说"无法识别该仓库地址"，
用户根本不知道原因（他填的是一个完全合法的 git 远端）。

只有两个能力真的依赖平台识别：**鉴权注入**（`credentialForRemote` 认不出平台就返回
undefined，回退到系统凭据助手）和**「在远端打开」**。

→ 改成宽松校验：只拦明显写错的输入（带空格的句子、中文），
非 GitHub/Gitee 的合法远端**放行但给不阻断的提示**（随输入实时显示），
留空仍然合法（用户想暂时断开同步）。

教训：**校验要区分「技术上必须」和「产品上倾向」**。
前者该硬拦，后者该提示 —— 把后者做成硬拦，会让用户在一个完全可用的场景里卡住。

## 用「死键扫描」收尾（同日晚）

写了个脚本（`.probe/check_unused_i18n.py`）扫出 locale 里**定义了但从未被引用**的键。
之前手工发现的 7 个死键就是这么来的，这次做成自动化的：229 个叶子键里 25 个未被引用。

分诊后分两类：

**通用词汇（留着合理）**：`common.*` 的十几个（ok / yes / no / retry / copy…）、
`notice.*`、`host.detecting`。这些是 UI 词汇表，留着比删了再加省事。

**「写了却没接上」的信号（都修了）**：
- `sync.mergeAborted` —— 用户点「放弃当前合并」后**毫无反馈**。撤销类动作静默完成，
  会让人怀疑到底成没成。→ `abortMerge` 成功后发提示。
- `installer.resolving` / `installing` —— 弹窗用笼统的「加载中…」，
  用户不知道卡在识别还是安装。→ `busy` 从布尔量改成阶段枚举。
- `installer.sourceRaw` —— 从源码装的插件更新检查查不到版本，用户会以为功能坏了。
  → 仅在 `channel === "raw"` 时在跟踪列表显示来源（常见情况不加噪音）。
- 绑定弹窗的空状态与扫描中没有底部按钮（只能按 Esc）→ 补上 footer。

**设计上就不该存在（删掉）**：
- `plugin.commandCategory` —— Obsidian 的命令 API **没有分类字段**，纯属臆想出来的键。
- `settings.title` —— 被 `cmdOpenSettings` 取代（我上一轮改命令命名时引入的）。

### 顺手记一条方法论
**死键是信号，不只是垃圾**。一个没人用的 i18n 键通常意味着：
① 漏接的本地化（对应英文界面下冒中文，或功能没接线）；
② 删功能时的残留。
两种情况都值得看一眼 —— 这次 4 个「写了没接上」全都是真缺口。

### 一个看走眼的
我一度以为 `removePluginFolder` 用朴素路径删目录（目录名≠id 那类插件的文件删不掉），
因为 grep 只匹配到文档注释里的 `getPluginFolder`。实际读实现后确认它**确实**用了
`resolvePluginFolder`，没有 bug。
**教训：grep 命中注释会误导判断，关键路径要读实现而不是看搜索结果。**

## 一个测试盲区：变异验证打偏才发现（同日晚）

死键扫描还揪出最后一个真缺口：`host.requestFailed` 写了没接上 ——
**意料之外的 HTTP 状态码**（500/502/422）会落到 `ObsyncError → err.message`，
中文用户在界面上看到的是 `Unexpected HTTP 500 from o/r (GitHub) while ...` 这句英文。

→ 新增 `HttpStatusError`（带 `status` + 服务端说明），`describeError` 加翻译分支。

**但更有价值的是过程中发现的测试盲区**：

我给这个修复写了几条用例，然后做变异验证 —— 把 `HttpStatusError` 换回 `ObsyncError`，
**结果用例照样全绿**。原因是我改错了文件：用例直接构造 `HttpStatusError` 对象
测 `Notifier`，而变异打在 `statusMapper`（抛出点）上，两者根本没接触。

改对变异目标（去掉 `notice.ts` 里的分支）后用例立刻变红，修复得到确认。

顺带暴露一个真问题：**`statusMapper` 此前没有任何测试**。它是「状态码 → 错误类型」
的唯一收口处，判定条件由各 host 提供，却没有用例覆盖两个平台各自的限流表达方式。
→ 新增 `statusMapper.test.ts`（10 项）。

**方法论**：变异验证不只是「确认测试有效」，它还能**暴露测试打在哪一层**。
如果注入 bug 后用例不变红，先别怀疑测试写得松 —— 先确认变异点和断言点是不是同一条路径。

### 死键清扫的最终结果
25 → 12。剩下的全是 `common.*`（ok / yes / no / retry / copy…）——
标准 UI 词汇表，留着比删了再加省事。其余逐个处理掉了：
4 个背后是真缺口（见上），1 个是早期设计残留（`sync.statusIdle` —— 状态栏空闲时
显示分支/ahead/dirty，比「就绪」有用得多），2 个设计上不该存在
（`plugin.commandCategory`：Obsidian 命令 API 没有分类字段；`settings.title`：被取代），
1 个接上了（`installer.checking` —— 检查按钮原本只置灰、不给"正在检查"反馈，

## 把「唯一待实测项」推进了一大步（同日晚）

交接文档里长期挂着一项：**对真实 Gitee 私有仓库 push 一次，确认
`http.extraheader` 的 Basic 认证被接受**。没有令牌做不了完整验证，但做了能做的部分。

### 先试了本地搭带鉴权的 git 服务器（走不通）
思路是起一个只认 Basic 的 HTTP 服务器、把请求转给 `git http-backend`，
然后用 simple-git 推上去。结果 `git http-backend` **这个 Git 安装里没有**
（`git help -a` 列了元数据，但执行报 `not a command`，二进制没随包发）。
本地验证这条路放弃。

### 改成对真实 Gitee 验证机制
`github.com:443` 当前被阻断（直连与代理都不通，`api.github.com` 正常），
而 `gitee.com` 通 —— 正好是目标平台。做法是**对照实验**：

- 不带凭据读公开仓库 → **成功**（对照组，证明网络与命令没问题）
- 带**伪造**的 Basic 头 → **被拒**（`could not read Username` = 服务器返回了 401 挑战）

两条同时成立才说明机制有效。**关键在于"被拒"是好事**：如果 Gitee 忽略这个头
（当匿名请求处理），公开仓库照样能读成功 —— 那就说明这个机制在它这里不成立。

→ 固化成 `tests/live/giteeGitAuth.live.test.ts`（3 项，5 秒）。
**剩下的未知只有「有效的私人令牌是否被接受」** —— 那是 Gitee 的账号策略，
文档写明支持，但没有令牌无法在此确认。

### 过程中踩的两个环境坑（都记进 HANDOVER 第七节）
- **`git ls-remote` 会撑爆 Node 的 `execFile` 缓冲**：默认 1MB，而
  `mindspore/mindspore` 实测 **18 万个引用**，报 `stdout maxBuffer length exceeded`。
  看着像网络问题，实则不是。挑测试仓库要选引用少的（`oschina/git-osc` 只有 33 个）。
- **401 之后 git 会调凭据助手，而系统级 `helper-selector` 在非交互环境里干等**：
  表现为「用例卡满 45 秒」，看起来像网络慢。加 `-c credential.helper=` 关掉它
  （**空值重置助手链**，这个语义很隐晦）。加完之后 93 秒 → 5.2 秒。

## 又发现一个性能缺口：装插件可能白等三分钟（同日晚）

起因是 live 测试里 GitHub 那条「安装前准备」超时。查下去发现是**真问题**：

安装器是**逐文件**回退的（`manifest.json` / `main.js` / `styles.css`），
每个文件都先试资产通道。而 http 层还会重试 2 次 × 20 秒超时 = 62 秒。
三个文件合计 **约 3 分钟**才装完 —— 而资产 CDN（`github.com` →
`objects.githubusercontent.com`）在国内网络下不可达是常态，
**正好打在目标用户身上**。

两处修复：
1. **http 层不再重试传输层失败**。超时 / DNS 失败 / 连接被拒是确定性的，
   再试两次只是把「等 20 秒」变成「等 62 秒」，而调用方的降级路径往往立刻能成。
   值得重试的是服务端临时故障（5xx / 408），那些会很快返回状态码。
2. **安装器记住资产通道失败**，后续文件直接走源码通道。只付一次超时。

→ 合计 3 分钟降到 20 秒。变异验证：去掉「记住失败」后资产端点被碰
**3 次而非 1 次**，正是那个"等三倍超时"的问题。

### 顺带发现：用户已经在真机上用起来了
测试库的 `data.json` 里有 **4 个真实跟踪的插件**（都是 release 通道），
更新检查也跑过并识别出 2 个可更新。说明核心链路在真实 Obsidian 里是通的。

## 发布就绪检查：minAppVersion 写低了（同日晚）

### 问题
`manifest.json` 的 `minAppVersion` 写着 **1.5.0**，但 `SecretStore` 调

### 一处我自己的误判（重要，记下来）
我最初判断 `minAppVersion` 时用的是
`grep -B6 "<成员>(" | grep -o "@since …" | tail -1`，

据此断言「1.5~1.10 会崩」并改成了 1.11.0。

**这是错的**：`-B6` 的范围跨进了**下一个成员**的注释块，`tail -1` 取到的是它的 `@since`。

### 新增 `pnpm check`（`scripts/checks.mjs`）

## 发版清单文档（同日晚）

新增 `docs/RELEASE.md` —— 把发版步骤、资产校验方式、以及**本机环境特有的坑**
固化成可照着走的清单，免得每次发版都重新推导、重新踩。

内容按七节组织：发版前检查 → 改版本号 → 提交推送 → 建 Release 与传资产 →
校验上传结果 → 发版说明草稿 → 发版后。

**几条从记忆里搬过来的坑（都实测过）**：
- `git push` 走 HTTPS 到 GitHub 会先卡 **97 秒**（系统级 `credential.helper=helper-selector`
  在非交互环境干等），绕过姿势是 `-c credential.helper=` 传空值重置助手链
- `gh auth status` **不可信**（常报未登录但 `gh auth token` 有有效令牌）
- 上传资产必须用 `gh release upload`，**不能用 `gh api --hostname uploads.github.com`**
  （`gh api` 会多拼一个 `api.`，全部 Bad Gateway）
- 校验资产**不要靠下载**（`github.com:443` 时段性阻断），用
  `gh api .../releases/tags/{tag} --jq '.assets[] | .name, .size, .digest'` 读回服务端算的 sha256
- release body 用 `--input <文件>`，别用 `-f body=`（中文和引号会被 shell 拆坏）
- 用 Git Data API 建的 tag **不触发** `on: push: tags` 工作流

写的时候顺手验证了清单里的命令确实能跑：仓库 API 可达（`main`、公开）、
**目前 0 个 release**（v0.1.0 会是首版）、`sha256sum` 在 Git Bash 可用。

**注意 `versions.json` 的语义**：它是「插件版本 → 该版本要求的最低 Obsidian 版本」，
值要和 manifest 的 `minAppVersion` 一致，**不是插件版本本身**。

## 新增「连接测试」：把「验证鉴权」做成功能（同日晚）

用户把令牌填进了插件（走 `app.secretStorage`，Obsidian 1.13.7 的系统级加密存储）。
我**没有去解它** —— 那正是 SecretStorage 存在的意义，去破解它是错的做法。
同时 `github.com:443` 仍被阻断，也没法拿 GitHub 做替代验证。

**换了思路**：与其要用户把令牌交给我，不如把「验证鉴权」做成插件里的功能 ——
用户随时一键跑，问题当场有答案。这比让我读他的密钥存储更合理，也是同步插件该有的东西。

### 实现
`syncService.diagnose()` 跑一条递进的检查链，任何一步失败就停：
git 可执行文件 → 是否 git 仓库 → 有没有远端 → 平台能否识别 → **真的 `ls-remote` 连一次**。
最后一条是关键：**令牌填了不代表有效，光看设置项判断不了**。

- `GitManager` 新增 `testRemoteAccess()`，用 `ls-remote` 而不是 `fetch` ——
  **只读**，不动 refs / index（有测试锁着这条性质）
- 结果是结构化的 `DiagnosticCheck { id, status, detail }`，文案由设置页按 `id` 取 locale，
  所以 `diagnose()` 不依赖 i18n、能单独测
- 「平台认不出」与「没配令牌」标成 `skipped` 而非 `failed` —— 它们只意味着注入不了令牌，
  用户仍可走系统凭据助手；报成失败会误导人去改一个没问题的配置

### 测试抓到一个隐式依赖
`diagnose()` 原本用 `notifier.describeError()`，而那依赖「`createSyncModule` 已注册过
翻译器」这个**隐式前提**。单独构造 `SyncService` 时，鉴权失败只显示英文技术描述。
→ 改成先用自己模块的 `describeSyncError`，再回退到 `notifier.describeError`。
**诊断是自包含工具，不该依赖模块装配顺序。**

新增 8 项诊断测试（含「网络不通与鉴权失败要能区分」「是只读的」）。

### 顺带把自查脚本修准了
新增的 UI 让三个扫描器都出现了误报，逐个修：
- **i18n**：`t.sync.diagnoseCheck[check.id]` 是动态索引，静态扫不到具体键名 →
  加规则：**父对象被 `[` 索引访问过，就视为整组键已用**
- **CSS**：类名可能出现在多类名字符串（`"obsync-badge obsync-badge-update"`）
  或跨行三元里 → 改成**全文扫 + 剥注释**，并维护带理由的 `NOT_A_CLASS` 表
  （`obsync-token-` 是密钥 id 前缀、`obsync-last-auto-` 是存储键前缀、
  `obsync-sync-view` 是视图类型标识）
- 把 `stripComments` 提成公共工具（扫描类检查都要先剥注释，否则注释里的类名/中文
  会被算成"用到了"，掩盖真问题）

变异验证：把 CSS 里的 `obsync-diag-ok` 改成不存在的类名，自查同时报出
「用了没定义」和「定义了没用」。扫描器从 20/20 提到 **25 用 / 25 定义**（更准了）。

## 又发现一个真缺口：初始化仓库不建 .gitignore（同日晚）

查「用户要走通验证还需要什么」时发现：OBSync 的 `init()` **只跑 `git init`**，
**完全没有 `.gitignore` 处理**（`grep -rn gitignore src/` 在业务代码里零命中）。

后果很实际：`.obsidian/workspace.json` 存的是面板与标签布局，**每开关一个标签它就变**。
多设备同步它必然冲突，而且冲突内容是整份 JSON，用户没法手工合并 ——
这是 Obsidian 同步最常见的坑。而用户不会预见到。

**佐证**：用户测试库的 `.gitignore` 是**别的同步插件**（`gitee-sync-plus`）建的，
里面正好排除了 `workspace.json` / `workspace-mobile.json` / `.trash`。
说明这事确实得有人管，而 OBSync 没管。

### 做法
初始化时**顺手建一份默认 `.gitignore`**，并明确告知建了什么（不偷偷摸摸）。
三条边界：
- **已有 `.gitignore` 时绝不覆盖** —— 用户可能有自己的规则，覆盖是数据损失
- **建不了也不让初始化失败** —— 只是少一层保护
- 模板**整段放在 locale** 里（含面向用户的说明文字），不在代码里拼

另加「编辑 .gitignore」命令，不存在就按同一份模板建出来 ——
空文件没法教人该忽略什么。

参考项目 obsidian-git 是给了「编辑 .gitignore」「加入 .gitignore」两个命令但**不自动建**。
我选了更主动的做法，因为「等冲突发生再处理」的成本高得多。

新增 3 项测试（建了 / 不覆盖已有 / 建不了也不失败）。

## 同一个根因的第三处表现：文件被重复计入（同日晚）

读 `commitMessage.ts` 时顺手查了它的**输入**，发现 `doCommitAll` 这样拼文件列表：

```ts
const files = [...status.staged, ...status.unstaged, ...status.untracked].map(c => c.path);
```

而 `mapStatus` 是**按 `git status` 的两位状态位分别归类**的 ——
「改了又暂存」的文件（`AM` / `MM`）两个位都非空，于是同时进 `staged` 与 `unstaged`。
结果同一个文件被列两次，`{{numFiles}}` 多算、`{{files}}` 重复。

**这和之前那个 `UU` 是同一个根因**（都是「按两位状态位归类」的副作用），
只是表现不同：
- `UU`（冲突）→ 列表里出现**三次**（我上轮修了）
- `AM` / `MM`（改了又暂存）→ 出现**两次**（这轮修的）

顺着查，同一个根因还有两处用户可见的地方：
- **状态栏的脏文件数**：`staged.length + unstaged.length + untracked.length` 直接相加
- **视图的变更列表**：同一个路径出现两遍，让人以为有两处改动

三处都改成**按路径去重**。变异验证：去掉去重后 3 条用例失败，
直接看到 `['a.md', 'b.md', 'b.md']` 这样的重复。

### 教训
**一个根因会在多个地方以不同形式冒出来。** 修 `UU` 那次我只修了视图列表，
没想到 `AM` / `MM` 是同一类问题、也没想到状态栏和提交信息也在算这个数。
现在这几处都留了注释说明**为什么必须去重**，免得下次又被"简化"掉。

## 移动端会加载失败 —— 发布阻断级（同日晚）

换个维度查（之前都在查「代码对不对」，没查过「能不能上架 / 移动端能不能用」）。

先按 Obsidian 上架规则扫了一遍：`createElement` / 静态样式赋值 / `innerHTML` /
`eslint-disable` 屏蔽 obsidianmd 规则 / `console.*` 泄漏 —— **全部合规**。

然后想到移动端。manifest 是 `isDesktopOnly: false`，而 `main.ts` **静态导入**了
同步模块 → `simple-git` → 它在**模块初始化阶段**就 `require("child_process")` /
`require("fs")`。移动端没有 Node 集成。

### 实证（不是推断）
写了 `.probe/probe_mobile_load.mjs`：把打包产物包进一个函数，
注入一个「对 node 内置模块抛错的 require」，加载 —— 等价于移动端的条件。

```
加载阶段抛错 ❌  require is not defined: fs
```

**官方文档佐证**：Obsidian 移动开发文档明确写「Node.js API 和 Electron API
在移动设备上不可用。**任何**对你的插件或其依赖的调用都**可能导致插件崩溃**」。

### 修法：动态 import（保住两边的能力）
最省事的做法是改成 `isDesktopOnly: true`，但那会丢掉移动端的**插件安装**能力
（那是 BRAT 的真实使用场景）。所以先试能不能让依赖链惰性化。

- 试 `require("./features/sync")` → esbuild **确实**做成了惰性（移动端模拟通过、
  启动测试 15/15）—— 但 **`require` 在 vitest 的 ESM 环境里不存在**，启动测试全挂
- 改用 **动态 `import()`**（`onload` 本来就是 async）→ 移动端模拟通过、
  启动测试 15/15、**esbuild 不产生额外分块**（仍然只有 `main.js`）

### 加进 `pnpm check` 守住
这个不变式很容易被破坏（谁顺手写回静态导入就白改了），而且**在桌面上测不出来**。
新增第 5 项检查「移动端安全」：从 `main.ts` 走一遍**静态**导入图，
看有没有触及依赖 Node 的裸模块。变异验证：把静态导入加回去，
自查立刻报出 `src/features/sync/simpleGitManager.ts → simple-git` 并指出改法。

> 注：`require(...)` 那条路走不通的教训值得记 —— **桌面端能跑不等于测试环境能跑**，
> 反过来也一样。改加载方式时必须两边都验。

## 轮次：查出 Gitee 鉴权的用户名 bug（发布阻断级）+ 把「证据链」转正

这轮从「还有哪些维度没查」出发，最后落到一个**真 bug** 和一类**工程问题**。

### 真 bug：Gitee 的 git Basic 认证用户名
`withAuth` 里用户名是 `credential.account ?? "git"`，而 `credentialForRemote`
**从来不设 `account`** —— 所以实际发出去的永远是 `git`。
文件头还写着「两个平台都只校令牌不校用户名（文档如此）」。

**这个假设对 GitHub 成立、对 Gitee 不成立。** Gitee 服务端原文
（官方仓库 issue I1BGZG）：

```
remote: Username, "oauth2" or "gitee.com" is supported as username
        when using access token to pull or push the repository
```

后果极隐蔽：**公开仓库照常能读**（不需要凭据），只有私有仓库的 push/pull 失败
—— 会被误判成「令牌不对」「权限不足」或「网络问题」。

修法：用户名是**平台差异**，按项目约定放进 host 层 —— 新增接口属性
`IRepoHost.gitAuthUsername`（和 `tokenInQuery` 同一位置、同一表达方式）：
Gitee → `oauth2`、GitHub → `x-access-token`。用 `oauth2` 而不是真实账号名，
是因为账号名要额外调一次 `validateToken` 才知道，而 `oauth2` 恒定可用。

变异验证：把 Gitee 的值改回 `git` → 两条用例同时失败
（单测级断言 + 上网级断言）。

### 工程问题：被文档引用的依据躺在 gitignore 里
`main.ts` 的注释把 `.probe/probe_mobile_load.mjs` 当「实测依据」引用，
`authWire.test.ts` 的注释引用 `.probe/probe_auth.mjs` —— 两个都在 `.gitignore` 里。
别人克隆仓库后找不到，注释就变成了无法复核的断言。

处理（**能做成测试的就做成测试**）：
- 移动端探针 → `scripts/verify-mobile-load.mjs` + `pnpm verify:mobile`
  （它需要构建产物，所以不能进 `pnpm check`，单列一步）
- 鉴权上网探针 → `tests/features/authHeader.test.ts`
  （它用本地 HTTP 服务器，**不需要网络也不需要令牌**，没理由不做成正式测试）
- 删掉 `.probe/` 里那两个已被取代的副本（两份并存只会漂移）

新测试锁的性质：**第一个请求就带上 Authorization，不等 401 挑战** ——
断言落在 `seen[0]` 上而不是「某个请求带过头」，后者在「先匿名再重试」的实现下
也会通过，但那不是我们要的行为。而且 config 由 `withAuth` 产出，
不在测试里手写键名（否则 `http.extraheader` 改名了用例照样绿）。

> 顺带：写这条测试时我把整个 `Basic <base64>` 当 base64 解码，得到一堆乱码 ——
> 测试抓住的是**我自己写错的断言**，不是产品代码的问题。

### live 测试实跑（2026-09-17 凌晨）
`pnpm test:live`：**12 通过 / 3 跳过**。
- Gitee git 端点的 Basic 鉴权 3 项**全通过** —— 那个挂了很久的
  「Gitee 服务端是否校验这个头」终于有了实测结论（伪造凭据被拒 + 匿名可读公开仓库）。
  文档里那条 ✅ 之前是照着断言写的，现在才是真跑过。
- GitHub 真实链路 4 项通过。其中资产下载走了降级路径
  （`github.com/.../releases/download/` 被阻 → 回退源码文件），
  说明那条降级是**真的在起作用**，不是防御性代码。
- Gitee API 的 3 项因匿名配额 403 跳过（符合预期，配 `OBSYNC_GITEE_TOKEN` 可跑）。

### 教训
1. **涉及「对端校验规则」的假设不要写成「文档如此」。** 要么实测，要么标注未验证。
   用户名那条就是照假设写的，而**单测永远发现不了** —— 我们构造出的 Basic 头
   本身是合法的，不合法的是对端接不接受这个用户名。
2. **被文档/注释当依据引用的东西，不能放在 gitignore 里。** 引用一个别人拿不到的
   文件，等于引用了一个无法复核的断言。有验证价值的就转成测试或 `scripts/`。
3. **能做成测试的探针就做成测试。** 鉴权上网那条探针一直「只是本地跑过」，
   而它其实不需要网络也不需要令牌 —— 白躺了好几轮。

`pnpm build` 通过并部署；`pnpm verify:mobile` 通过。

## 轮次：把「有效令牌被接受」这一步也自动化了（最后一环）

上一轮修了 Gitee 用户名，但那是**二手证据**（Gitee 官方 issue 里的服务端报错原文）。
这轮想当场复现，结果发现了更有用的东西。

### 想复现，但发现复现不了 —— 而「复现不了」本身是重要结论

用伪造令牌对比不同用户名打 Gitee 的 fetch 端点，**四种用户名
（`git` / `oauth2` / `gitee.com` / 随机串）返回的是完全相同的通用 401**
（`[session-xxx] git: Incorrect username or password (access token)`，
前缀只是把用户名回显出来）。

而 `Username, "oauth2" or "gitee.com" is supported as username...` 那句带
**`remote:` 前缀** —— 那是 **receive-pack（push）路径的服务端钩子**发的，
fetch 路径根本走不到。

→ **推论：`ls-remote` 这类诊断发现不了用户名问题。** 也就是说
「设置 → 连接测试」（我上一轮加的那个功能）**验证不了这件事**。
这解释了为什么它挂了那么多轮都没结论 —— 不是没人跑，是**跑法不对**。

### 但 GitHub 那一半我验成了

`gh auth token` 其实**有效**（`login=Dyse-Sofqi`，`gho_` 开头）——
之前以为没有，是因为找错了路径：Windows 上 gh 的配置在
`%APPDATA%\GitHub CLI\hosts.yml`，**不是** `~/.config/gh/hosts.yml`。
而 `github.com:443` 这轮也通了，于是可以做真实的端到端验证。

在**私有仓库** `Dyse-Sofqi/bewater` 上用生产同款机制实测：

```
不带凭据         退出码=128  ← 对照组，必须失败
x-access-token   退出码=0  读到 1 个分支
git              退出码=0  读到 1 个分支
oauth2           退出码=0  读到 1 个分支
Dyse-Sofqi       退出码=0  读到 1 个分支
```

两条结论：① 整条链路（config → `-c` → HTTP 头 → 服务端接受）在真实私有仓库上跑通；
② **GitHub 确实不校验用户名**（四种全通），所以改成 `x-access-token` 对 GitHub 无害。

### 固化成 `tests/live/privateRepoAuth.live.test.ts`

可选启用：`OBSYNC_LIVE_PRIVATE_REPO`（+ `OBSYNC_LIVE_TOKEN`，GitHub 上省略并回退
`gh auth token`），未配置时**整组跳过**（用 `describe.skipIf`，不是用例里 return ——
后者会显示成「通过」，等于假装验过了）。

结构是**对照组 + 接受**：
1. 不带凭据必须**失败** —— 缺了这条，「成功」什么也证明不了（公开仓库也成功）
2. 带 host 层声明的用户名 + 令牌必须成功 —— 用户名从 `withAuth` 同一套代码推导，
   所以这条同时锁住「用户名改错」的回归
3. 再加一条断言 host 层用户名与平台匹配（Gitee 必须是 账号名/oauth2/gitee.com 之一）
4. `OBSYNC_LIVE_ALLOW_PUSH_DRY_RUN=1` 时多跑一条 push 预检 ——
   只有它能触发 Gitee 的用户名白名单。默认关闭，因为它属写路径
   （`--dry-run` 不发送对象也不更新引用，但仍会建立 receive-pack 会话）

变异验证三条：未配置 → 4 条全部跳过（不是"通过"）；指向**公开**仓库 → 对照组失败
并给出「请换一个真正的私有仓库」的解释；把 Gitee 用户名改成 `git` →
`expected [ 'oauth2', 'gitee.com', 'oschina' ] to include 'git'`。

### 剩下的

唯一没验的还是**有效 Gitee 令牌被接受**（我没有 Gitee 令牌，只有 GitHub 的）。
但现在有了可复用的跑法，你配上 `OBSYNC_LIVE_PRIVATE_REPO` + `OBSYNC_LIVE_TOKEN`
一条命令就能收尾 —— 比点「连接测试」强，因为连接测试走 fetch、验不到用户名那一环。

验证：`pnpm check` 5 项全通过；`pnpm test` 304 项全绿（29 个文件）；
`pnpm build` 通过并部署；`pnpm test:live` 12 通过 / 7 跳过（3 条 Gitee 配额 + 4 条未配置）。
