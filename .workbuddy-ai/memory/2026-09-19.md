## 轮次：`requestedVersion` 一直存在，而界面上没有它的入口

### 问题

`requestedVersion`（「用户要求的版本」）是这个项目里一个**写了却没有入口**的字段：

- `install()` 每次都把它写进记录（`recordItem`），`reinstall()` 读它（重装装回那一版）；
- 而界面上**只有**「添加插件仓库」弹窗写过它一次 —— 装完之后既改不了、也**看不见**。

后果很具体：一个装坏了的版本，除了等作者发新版没有别的出路。而「退回上一版」恰恰是
遇到坏版本时最该能做的事（参考项目 BRAT 有 frozen-version，就是这个用途）。

这和 `sync.enabled`（那个「死开关」）是同一类问题，只是方向相反：
那里是**开关有效果但没人读**，这里是**字段有效果但没人写、也没人显示**。

### 做法：给跟踪列表加第七个按钮，只有插件有

- 新弹窗 `ui/VersionManagerModal.ts`：列出该插件已发布的版本，选一个切换过去。
  三条刻意的设计 ——
  1. **认得出当前版本**：磁盘上装的那一版标「当前」（`1.2.3 · 当前`）。一串 tag 里
     认不出自己在哪一版，「退回上一版」这个动作就无从下手；
  2. **默认选中记录里的选择**（不是「最新版本」）。默认成「最新」会把这个控件变成一个
     不断把用户往最新版拽的东西，而他要确认的是「我钉在哪一版」；
  3. **「没有版本可切」与「这次没拉到」分开说**。前者是这个仓库的事实（Gitee 上
     「只有源码、不发 release」是常态），后者是请求失败、可以重试。混成一句，
     用户会去重试一件永远不会成的事。
- 执行走 `install()`（**不是** `reinstall()`）：要装的正是用户刚选的那个 tag，
  而 `install` 会把它写回记录 —— 也就是**钉在这一版**。于是三条现成语义一起成立：
  重装装回它；「更新到最新版本」/「更新全部」把记录改回 `latest`（解开钉住）。
- **列表上加「已固定 \<tag\>」徽标**：这个状态只在 `data.json` 里，而它的后果是
  「重装会装回旧版」。不显示的话，用户看到旧版本号分不清是自己选的还是更新失败留下的。
  徽标措辞刻意与「已冻结」区分：冻结 = 不参与检查，钉住 = 认准这一版但**照常检查**。

### 只有插件有（刻意的不对称）

主题在设计上就没有版本钉选（`TrackedTheme` 上没有 `requestedVersion`，
`updateTheme()` 永远按最新走）。给主题一个能选版本的按钮，等于承诺一件做不到的事，
所以它不出现 —— 用例把这条不对称钉住了（插件 7 个按钮、主题 6 个）。

> 要给主题也加，得先给它一个「钉住」的概念（字段 + `updateTheme` 收版本参数）。
> 那是**产品决定**，不是顺手能实现的细节，所以本轮没做。

### 一个容易写错的判据

**「当前」标记必须用版本比较，不能用字符串相等**：release tag 常带 `v` 前缀
（`v1.2.3`），而 manifest 里的 version 不带（`1.2.3`）—— 字符串相等时
「当前」两个字永远不会出现，而用户到这里来正是为了认清「我在哪一版」。
改用 `compareVersions`（`semver.coerce` 归一，与更新检查同一判据），
非 semver 的 tag 才退化成相等比较。

### 变异验证（四个方向，全部被抓住）

| 变异 | 被哪条用例抓住 |
| --- | --- |
| `switchVersion` 改传 `"latest"`（等于「回退」永远失效） | 「按那个 tag 安装」 |
| 「当前」标记退回字符串相等（`v1.2.0` 认不出） | 「不同形时照样认得出」 |
| 去掉「已固定」徽标（状态重新变成不可见） | 「挂已固定徽标」 |
| 让主题也拿到那个按钮（承诺做不到的事） | 两处不对称用例同时失败 |

新增 17 条用例：`versionManagerModal.test.ts` 13 条（列表状态 / 当前版本标记 /
默认选中与提交），`trackedItemsList.test.ts` 4 条（接线 / 执行 / 徽标 / 主题不对称）。

### 记一条方法上的事

这轮修的是「**字段有效果、界面没有入口**」这一类洞 —— 它和上一批修过的
「开关有效果、没人读」是镜像关系。两者都**不是**类型或测试能自动发现的：
类型上 `requestedVersion: string` 完全合法；测试里没人会去点一个不存在的按钮。
`scripts/checks.mjs` 的第 6 项（设置项无人读取）只覆盖后一个方向，
前一个方向目前只能靠**逐个字段问「它从哪写、在哪显示」**。

验证：`pnpm check` 6 项全通过；`pnpm test` 全绿；`pnpm build` 通过并部署到两个库
（`F:/_Workspace/Plugin-Test` 与 `D:/_Workspace/learning-records`）。

## 轮次：真机上装不上 Trefoil —— 报的是 `missingRequiredFiles: main.js`

用户贴来一段控制台日志（他刚装上新版、去点插件行上的按钮）：

```
[OBSync] operation failed installer error [missingRequiredFiles]
{"repo":"Dyse-Sofqi/Trefoil","files":"main.js","of":"plugin"}
```

问「为什么会这样」。查下来是**两个真 bug 叠在一起**，而且第二个是「报错指错方向」。

### 先确认事实（不要凭感觉）

```
gh api repos/Dyse-Sofqi/Trefoil/releases  → 1.0.0~1.0.3，每个都带 main.js/manifest.json/styles.css
仓库 tree（HEAD / 1.0.3 / 1.0.0）        → 没有 main.js，也没有 styles.css（都是构建产物）
本机下载同一个资产四次                   → 25s 超时 / 16.8s 成功 / 0.6s / 0.6s（raw 域名同一时刻 485ms）
```

也就是说：**文件确实在 release 里，只是这一次没下下来**。而 http 层的超时阈值是
20 秒 —— 16.8 秒那种「成功」就压在边界上，所以同一条 URL 一会儿成一会儿败。

### bug 1：那条「短路」把一次本可成功的安装变成了失败

`fetchFromRelease` 里有一条优化：某个文件的资产因传输层失败后，**后续文件不再试资产**
（为的是别白等三次超时）。但它的作用范围写宽了：

1. `manifest.json`（第一个文件）的资产在冷连接上超时 → 回退源码成功 → 记住「资产不通」；
2. `main.js` 于是被**跳过资产通道**，只去源码里找；
3. 而它是构建产物，仓库里没有 —— 于是「源码里找不到」被当成「这个插件缺 main.js」。

而按实测，那个被跳过的资产**重试一次只要 0.6 秒**。所以现在：**任何文件在源码里也
拿不到时，为它单独重试一次资产通道**（资产干净地 404 时不重试 —— 那是远端确实没有）。
代价最多一次超时，而那条路径本来就要失败。

顺带发现同一处还有第二个受害者：`styles.css` 也被跳过（Trefoil 同样是构建产物），
**原来会静默装出一个没有样式的插件** —— 插件能跑、界面是坏的，而且没有任何提示。
同一处修复一并覆盖。

### bug 2：报「找不到 main.js」，把用户指去检查一个没问题的地方

原来的报错只有一种 `missingRequiredFiles`（「找不到 X，无法安装该插件」）。可是
「缺文件」有两种完全不同的成因，下一步动作也完全不同：

| 成因 | 用户该做什么 |
| --- | --- |
| 仓库/资产里确实没有它 | 去看作者的发布流程（或自己补发） |
| 挂在那儿但没下下来 | 检查网络、重试、换 Gitee 镜像 |

现在用 release 的资产名判定，第二种报 `assetDownloadFailed`（新类型码 + 中英文案）。
顺带发现 `missingBuildArtifacts` 这个键**写了却从来没抛出过**（死键，只是被
`describeInstallerError` 引用所以自查扫不到）—— 留着，见「保留但未接线」那套先例。

### 变异验证（两个方向都被抓住）

| 变异 | 被哪条用例抓住 |
| --- | --- |
| 去掉「资产 404 就不重试」的判断 | 「资产 404 时不为它重试」 |
| 去掉 `assetDownloadFailed` 分类 | 「资产挂着却没下下来」+「资产 404 时不为它重试」 |

新增 4 条用例（`installFiles.test.ts` 19 条）。**一条老用例按新规则改了期望**：
「资产通道网络不可达时，后续文件不再试它」—— 短路现在只对「源码里拿得到的文件」生效，
所以 `downloads` 里多了 `styles.css`（它只有资产里才有）。这条改动是**有意的行为修正**，
不是为了让测试变绿。

### 一句提醒（写给下次的自己）

`missingRequiredFiles: main.js` **不等于**「作者没上传 main.js」。先看 release 里有没有它，
再决定是查网络还是查发布流程 —— 我这次差点顺着「构建产物没提交」这个思路查错方向，
是先去读了真实仓库的资产列表才拐回来。

验证：`pnpm check` 6 项全通过；`pnpm test` **697 项全绿**（51 个文件）；`pnpm build` + 部署。

## 轮次：两件用户直接提的事 —— 「显示加载动画」与「为什么它不走 Gitee」

用户的第二、三句话（接着上一次的失败）：

> 获取插件时，请显示加载动画，不然我根本不知道你是不是在更新。另外 Trefoil 插件我选了
> 1.0.2 旧版安装，但是他却不走 gitee 路线，也找不到选择 gitee 镜像下载的选择

### 先查事实：Trefoil 到底有没有 Gitee 镜像

有，而且**比 GitHub 快一个数量级**（同一时刻实测同一个 `main.js`）：

| 来源 | 实测 |
| --- | --- |
| `github.com/Dyse-Sofqi/Trefoil/releases/download/1.0.3/main.js` | 25 秒超时 ／ 16.8 秒 ／ 0.6 秒 ／ 0.6 秒（963 KB） |
| `gitee.com/sofqi/Trefoil/releases/download/1.0.2/main.js` | **200，3.1 秒**（939 KB） |

`gitee.com/sofqi/Trefoil` 有 1.0.2 与 1.0.3 两个 release，资产齐全
（`main.js` / `manifest.json` / `styles.css` + zip + tar.gz）。而 `gitee.com/Dyse-Sofqi/Trefoil`
**404** —— 这正是探测失败的原因：

自动探测只猜两个候选（`findGiteeMirror` 的 `mirrorOwnerCandidates`）：
1. **同名 owner**（`Dyse-Sofqi`）→ Gitee 上没有 → 不成立；
2. **你 Gitee 账号名下的同名仓库**（`sofqi`）→ 但账号名要调 `GET /v5/user` 解析，
   **那需要 Gitee 令牌**。

用户没填 Gitee 令牌时，两个候选都不成立 → 探测永远找不到它。**而界面上没有任何入口**
能把这第三个地址指出来 —— 这就是「找不到选择 gitee 镜像下载的选择」的由来。
（跟踪列表里那条「疑似镜像 · 尚未使用，待确认」也帮不上：提议只在**安装成功之后**才写入，
而那次安装正好失败了。）

### 做法

1. **「版本管理」弹窗里加一节「下载来源」**：开弹窗时跑一次探测（`probeMirror`，只提议），
   探到就给「改用 Gitee 镜像」按钮；**探不到也要解释为什么**（只猜两个候选，别的账号下就手填）。
2. **手填镜像地址**（`InstallerService.setMirror`）：自动探测的兜底。校验用 manifest 的 `id`
   —— 与自动探测同一条判据，**不一致直接拒绝**（`mirrorIdMismatch`），因为只比仓库名会装错东西。
   确认之后走既有的 `confirmMirror`：主来源换成它、原来源进 `origin`。
3. **换完来源必须重拉版本列表**：列表是从当前来源查的，换了仓库 tag 可能完全不同
   （Trefoil 的 Gitee 只有 1.0.2 / 1.0.3，GitHub 有四个）。不重拉就会给用户一个
   「来自旧仓库、点了会失败」的列表。
4. **「在跑」看得见**（用户第一句话）：两层反馈，可见性条件不同所以都要有 ——
   - 被点的图标按钮换成会转的 `loader`（`.obsync-spinning`）：**不受**「显示操作结果提示」设置影响；
   - 带圆环的进度提示，按文件更新文案（「Trefoil：正在获取 main.js…」）：受该设置控制
     （与设置页里那句说明一致）。
   逐文件进度本来就是现成的（`fetchFiles` 一直有 `onProgress`），这次才接到 UI：
   `InstallRequest.onProgress` → `fetchItem` → `fetchFiles`，`updateTheme` / `reinstall`
   各加一个可选参数；行内四条动作统一走 `runWithProgress`。

### 变异验证（四个方向）

| 变异 | 被哪条用例抓住 |
| --- | --- |
| `startSpinner` 不换图标（等于没有转圈） | 「点更新之后按钮变成会转的 loader」+「检查更新同样转圈」 |
| `install` 不再把 `onProgress` 传下去 | 新加的「取文件时逐个回报文件名」（见下） |
| `setMirror` 去掉 id 校验 | 「**id 不一致时拒绝采用**，记录一动不动」 |
| 换来源后不重拉版本列表 | 弹窗两条「…并按新来源重拉版本」 |

### 一次真实的测试盲区（值得记下来）

第一轮变异里，「不再传 `onProgress`」**没有被任何用例抓住** —— 因为那条 UI 用例的替身
服务自己调了 `request.onProgress`，验的是「UI 把回调交出去了」，**没验服务有没有一路
传到 `fetchFiles`**。补了一条走真实 `InstallerService`（只 mock HTTP）的用例：
`install({ onProgress })` 与 `reinstall(item, onProgress)` 都必须按
`manifest.json → main.js → styles.css` 回报。补完之后那个变异立刻被抓住。

教训与「装配层的接线」是同一类：**替身越靠近被测层，越容易漏掉中间那一跳**。

验证：`pnpm check` 6 项全通过；`pnpm test` **714 项全绿**（51 个文件）；`pnpm build` + 部署。

## 轮次：从 Gitee 镜像地址装 Trefoil 又失败 —— `String(undefined)` 是真值

用户贴来的日志（三条一样的形状）：

```
[OBSync] downloading asset manifest.json for sofqi/Trefoil failed,
         falling back to the source file at 1.0.3 …
installer error [assetDownloadFailed] {"repo":"sofqi/Trefoil","files":"main.js","of":"plugin"}
```

### 先量，再猜

同一台机器、同一时刻：

| 请求 | 结果 |
| --- | --- |
| `gitee.com/sofqi/Trefoil/releases/download/1.0.3/main.js`（匿名） | **200，963,711 字节，2.8 秒** |
| 同一个 URL 带一个**伪造**令牌 | 200（令牌不影响） |
| `gitee.com/api/v5/repos/sofqi/Trefoil/releases/1152200/attach_files/undefined/download` | **404** |

最后那条就是我猜的「插件实际会去请求的地址」——一次就命中。再看 Gitee 返回的资产原始 JSON：

```json
{ "browser_download_url": "https://gitee.com/sofqi/Trefoil/releases/download/1.0.3/main.js",
  "name": "main.js" }
```

**没有 `id`**（连 `size` 都没有）。而实现里写的是 `id: String(asset.id)` ——
缺字段时得到字符串 `"undefined"`，**它是真值**，于是：

```ts
if (token && release?.id && asset.id) {   // "undefined" 通过了这个判断
    url = `${API}/repos/${id}/releases/${release.id}/attach_files/${asset.id}/download`
    //                                    ↑ 字面量 undefined → 404
}
```

所以症状**只出现在配了 Gitee 令牌的人身上**（那条分支要 token 才进）——这也解释了
为什么我匿名测什么都好、用户却全 404。三个资产各 404 一次，回退源码后 `manifest.json`
在仓库里有、`main.js` 是构建产物没有 → `assetDownloadFailed: main.js`。与日志逐字对上。

### 修法（两处）

1. **缺字段就保持缺席**：新增 `optionalId()`，`mapRelease` 不再造 `"undefined"`；
   `GiteeAsset` 的 `id`/`size` 改成可选（照实测形状写类型）。
2. **附件端点失败时回落到公开下载地址**（带同一个令牌）：令牌过期、企业版差异、
   资产 id 变了，在 Gitee 上都表现为 404 —— 一条可选通道失败不该让整次安装失败。
   与 GitHub 的 raw → contents 回退同一个道理。

GitHub 侧不受影响：它的 `asset.id` 从来没被用来拼 URL（走 `apiUrl`），而且 GitHub
的 API 契约保证这些字段存在。

### 这一组用例之前**一条都没有**

`GiteeHost.downloadAsset` 在那个 bug 存在期间**零用例**。更值一提的是：**已经有的那条
映射用例把 fixture 按类型写的、不是按实测写的** —— 它给资产造了 `id: 991` 与
`size: 1234`，于是「字段缺席」这条路径从来没进过测试。

新增 6 条：映射（真实形状 → `id` 必须是 `undefined`，不能是 `"undefined"`）、
无 id 时不去碰附件端点（并断言 URL 里没有 `attach_files`/`undefined`）、
有 id 时优先附件端点、附件端点 404 → 回落、两条都失败才报错、无令牌不带 access_token。

### 变异验证（两个方向）

| 变异 | 被哪条用例抓住 |
| --- | --- |
| `optionalId(asset.id)` 退回 `String(asset.id)` | 「资产没有 id / size 时也是合法响应」→ `expected 'undefined' to be undefined` |
| 去掉附件端点的回落 | 「附件端点失败时回落到公开地址」→ 报出的正是用户日志里那句 `… was not found while downloading main.js: Not Found` |

### 一条通用教训（值得写进接手文档）

**测试 fixture 必须按实测响应写，不能按类型写。** 类型是我们自己写的（`id: number`），
平台可以随时不给这个字段；fixture 跟着类型走，就永远测不出「字段缺席」。
`String(x)` 这种「顺手转一下」的写法是这类 bug 的温床：它把缺席变成了一个真值字符串。

验证：`pnpm check` 6 项全通过；`pnpm test` **720 项全绿**（51 个文件）；`pnpm build` + 部署。

## 轮次：确认镜像的页面让人「去核对」，却没给能点开的地址

用户原话：

> 在让用户确认是否为镜像的页面中，应该提供疑似镜像的地址供用户打开跳转，方便用户核实

这一页自己写着「核对方式：打开镜像仓库，看它的作者、主页或 README 是否指向源仓库；
两边的最新版本号也不该差太多」—— 而两个地址都只是 `<li>` 里的**纯文本**。
用户要照做，就得手抄或复制粘贴到浏览器里。**在最需要「看一眼」的地方留了一道摩擦**，
而且这一页的全部意义就是让人去看那一眼（判据只有「两边 manifest 的 id 相同」，
证明不了是同一份代码、同一个作者）。

### 做法

- 新增 `ui/repoLink.ts`：`appendRepoLink(containerEl, ref, text, t, cls?)` →
  `<a href={repoWebUrl(ref)} target="_blank" rel="noopener" title="在浏览器中打开仓库">`。
  用真正的锚点而不是自己接 onClick —— Obsidian 会把外链交给系统浏览器，
  参考项目（obsidian-git `descEl.createEl("a", { text, href, attr: { target: "_blank" } })`、
  BRAT 同样）都是这么写的；顺带拿到**右键复制链接**与 Tab 聚焦。
- 确认页的清单改成「前缀文字 + 可点开的地址」（地址本身就是链接文本，不另挂按钮）。
- 版本管理弹窗里那条「发现疑似镜像：…」也一样 —— 那里也是用户做同一个判断的地方。
- 文案因此拆成前缀与地址两段：`mirrorSourcePrefix` / `mirrorCandidatePrefix` /
  `versionMirrorFoundPrefix`；被取代的 `mirrorConfirmSource`、`versionMirrorFound` 删掉。
  `mirrorConfirmCandidate`（拼好的整句）**保留** —— 「添加插件仓库」弹窗用它当设置行名，
  而且与确认页共用同一个模块级常量 `mirrorCandidatePrefix`，不会出现两份措辞。

### 两个替身的坑（都补了）

1. **`appendText` 替身里没有**：真实 Obsidian 有，而且「前缀 + 链接」这种写法必须用它，
   不补的话测试里一跑就 TypeError（真机反而正常）。按 `tests/setup.ts` 里那句
   「替身少了任何一个，对应那一页就只会在真机上炸」的规矩补上了。
2. **`createEl` 的顶层 `href` 选项替身不认**：第一版写成
   `createEl("a", { text, href, attr: { target } })`（照 obsidian-git 的写法），
   而替身只处理 `text`/`cls`/`attr` —— 于是「它到底指向哪里」这条最该钉住的性质
   **在单测里断言不到**（`attrs.href` 是 undefined）。改成把 `href` 也放进 `attr`：
   落进 DOM 的属性完全一样（`setAttribute`），而测试看得见。

### 变异验证

| 变异 | 被哪条用例抓住 |
| --- | --- |
| 把 `<a>` 换回纯文本（`createSpan`，即修复前的样子） | 确认页那条 + 版本弹窗那条同时失败（都找不到 `<a>`） |

验证：`pnpm check` 6 项全通过；`pnpm test` **721 项全绿**（51 个文件）；`pnpm build` + 部署。

## 轮次：删掉「重装」按钮（它与「版本管理」重合），圆箭头还给「检查更新」

用户原话：

> 版本管理和重装是不是功能有些重合，如果是的话，那么删除重装按钮，把重装按钮的图标
> 留给检查更新按钮使用。

### 先把「重合」查实（不要凭感觉）

| 动作 | 插件实际调用 | 主题实际调用 |
| --- | --- | --- |
| 重装 | `install({repo, version: tracked.requestedVersion, enableAfterInstall: true, …})` | `updateTheme(item)` |
| 版本管理（默认选中的**就是** `requestedVersion`） | 同一组参数调同一个 `install()` —— **逐字相同** | —（主题没有版本管理） |
| 更新到最新（主题那行的 ⬇） | — | `updateTheme(item)`，与重装**一字不差** |

所以不只是「有重合」，而是：**插件那边重装是本弹窗的一个特例，主题那边两件事是同一件事**。
删掉它**没有丢任何能力**：插件要修复安装就是「打开版本管理 → 直接点切换」，主题走
「更新到最新」。

### 做法

- 删按钮；删 `InstallerService.reinstall`（没有生产调用方了 —— 留着就是死代码，
  而这个项目的规矩是删掉或明确标注）；删 `reinstall` / `reinstalled` 两个 i18n 键
  （死键会被自查第 3 项拦住）。
- 图标：`refresh-cw` 还给「检查更新」。这个图标本来就是它的 —— 当年因为和重装的圆箭头
  撞车才换成放大镜（旧注释还在：「和『重装』的圆箭头几乎分不出来」）。重装没了，撞车消失。
- 行内动作的图标改成模块级 `ICON` 常量。

### 差点漏掉的一处（测试抓住的）

图标在**两处**出现：`setIcon()` 一次、`runWithProgress()` 一次（做完要把图标换回来）。
我只改了前者，转完圈又变回放大镜 —— `trackedItemsList.test.ts` 的「检查更新同样转圈」
当场报 `expected 'search' to be 'refresh-cw'`。

**这正是提 `ICON` 常量的理由**：同一条事实写在两处，就等着漂移。三个行内动作现在都取
同一个常量。

### 文档同步

README（中英）、HANDOVER（五点七节新增「为什么删掉重装」+ 图标那段的来龙去脉）、
RELEASE.md 的发版说明草稿都跟着改了 —— 用户可见的能力少了，说明书不能还写着。

验证：`pnpm check` 6 项全通过；`pnpm test` **720 项全绿**（51 个文件）；`pnpm build` + 部署。
