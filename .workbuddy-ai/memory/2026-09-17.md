## 轮次：同一个事实写了四份，其中一份决定用户数据的生死

上一轮的问法是「同一概念有几处实现、差别会不会被用户看见」，并找到了更新检查
与安装路径的退化。这轮把同一个问法用在一个更基础的事实上：**「有哪些平台」**。

### 发现：一份声明 + 三份副本

```
host/types.ts       export type HostKind = "github" | "gitee"      ← 类型层
host/hostRegistry   export const SUPPORTED_HOSTS = [...]           ← 声明了，但**零调用方**
core/settings       const VALID_HOSTS = new Set(["github","gitee"]) ← 持久化校验
core/secretStore    for (const host of ["github","gitee"] as const)  ← 令牌快照
settingsTab          this.renderTokenField("github"); ...("gitee")   ← 令牌输入框
```

`SUPPORTED_HOSTS` 名字起得像唯一来源，实际是个**装饰品** —— 它自己也是第四份副本，
而且没有任何调用方（`pnpm check` 的「未使用 i18n 键」自查管不到代码）。

四处里最要命的是 `settings` 那份：它是 `data.json` 的**持久化校验**。
漏掉一个平台的后果不是「不好看」，而是用户在**那个平台**上装的插件，
下次加载 `data.json` 时被当成非法条目**无声丢弃** —— 不报错，列表里就没了。

而 `hostRegistry` 的注释写着「将来加 GitLab / Bitbucket 只需要在这里注册一项，
两个功能模块都不用改」—— 照着做会漏掉上面那三处。

### 修法

- `SUPPORTED_HOSTS` 移进 `host/types.ts`（**数组**，因为要有值而不只是类型），
  `HostKind` 由它推导：`(typeof SUPPORTED_HOSTS)[number]`。加平台 = 改那一行，
  类型层自动跟上。
- 三个使用点全部改为派生：`new Set<string>(SUPPORTED_HOSTS)`、
  `for (const host of SUPPORTED_HOSTS)`、`for (const host of SUPPORTED_HOSTS) renderTokenField(host)`。
- `hostRegistry` 的注释改成「加平台要动哪些地方的**完整清单**」（含第 3、4 步：
  `repoRef.ts` 的域名映射、i18n 文案）。
- 删掉 `hostRegistry.hostFor` —— 与 `getHost(ref.host)` 完全等价，后者已在 10 处使用。

### 顺带清了一遍死导出（方法先于结论）

项目已有「未使用 i18n 键」自查，理由是「死键是信号」，但**代码没有同类检查**。
于是先写扫描脚本，判据收紧了两轮才可用（第一版把「跨模块复用的类型声明」全算进来了）：

1. 只扫 `export function|const|class`（类型导出天生可能只写一次）；
2. 统计该名字在**整个 src 树**里的出现次数，先剥注释 —— 否则注释里提到也算；
3. **还要剥 barrel 的 `export { … } from`** —— `hostRegistry` 里那句
   `export * from "./types"` 会把死导出全盖住（这个坑差点让我漏掉东西）。

剩下声明处那一次 = 没有生产调用方。结论分两类，**处理方式不同**：

**已删**（是「重复实现里躺着的那一份」）：
- `InstallerService.checkForUpdate` —— 「有没有更新」的第二份实现。判据用
  `requestedVersion`，而跟踪最新版的插件那个值是字符串 `"latest"`，
  于是它**几乎恒返回 release**。谁把它当现成工具接上，谁就得到一个恒报「有更新」的功能。
- `manifest.isManifestCompatible` —— 纯转发。它声明的存在理由「注入
  `requireApiVersion` 便于测试」已被 stub 的 `__setApiVersion` 取代。
- `hostRegistry.hostFor`。

**保留但未接线**（是**只做了一半的功能**，不是垃圾）—— 按
`fileWebUrl` / `commitWebUrl` 那次的先例（当时也记作「死代码」，实际是漏做的功能）：

| 名字 | 缺什么 |
| --- | --- |
| `remoteLinks.commitOnRemoteUrl` | 「查看某个提交」的入口（同文件的另两个各有命令 + 右键菜单） |
| `GitManager.log()` / `CommitInfo` | 有实现体、零调用方 —— 提交列表本身躺在这儿 |
| `settingsTab.createSettingsTab` | 注释说「供测试与将来复用」，实际没人用；实现是 `void app`（参数是摆设，签名会误导） |
| `pluginFolder.isPluginInstalled`、`repoRef.isSameRepo` / `formatRemoteUrl` | 只有测试引用 |

> **教训**：`remoteLinks` 那条其实连着「源码控制视图」这条未做的主线。
> 下次再看到「死代码」，先问「这是残留，还是漏做的功能的一半」——
> 直接删会把半成品一起删掉。

### 这轮最有价值的一条：**测试与类型检查负责不同的漂移方向**

新测试 `tests/host/hostRegistry.test.ts`（5 条）刻意**不列平台名**，
而是让四个使用点互相印证：

- 每个平台都注册了 provider，且 **`host.kind` 与列表项一致**（复制粘贴写错
  `gitee: new GitHubHost()` 只有这样才能抓 —— 类型看不出来，两个类都满足 `IRepoHost`）；
- 每个平台都能走一遍 `repoWebUrl → parseRepoRef` 回到自己（域名映射漏一个，
  该平台的地址会被报成「不是 GitHub 或 Gitee」）；
- `normalizeSettings` 接受所有受支持平台（**条目无声消失**那条）；
- `secretStore.snapshot()` 覆盖所有平台；
- 外加一条**兜底前提**（列表非空且无重复）—— 上面四条都是「遍历 + 断言」，
  数组一旦空了循环体一次都不跑、全部照样绿。

**四个漂移方向变异**：`VALID_HOSTS` 写死成一个平台 → 1 条失败；
`snapshot` 循环只走一个平台 → 1 条失败；注册表复制粘贴写错 → 1 条失败；
域名映射少一个 → 1 条失败。

**第五个方向（测试的盲区，由 `tsc` 兜住）**：从 `SUPPORTED_HOSTS` 里**删掉** `"gitee"`，
那 5 条测试**全绿**（循环体少跑一次而已），但 `pnpm typecheck` 报 **31 个**错误
（`Record<HostKind, IRepoHost>` 的多余属性、`"gitee"` 与 `"github"` 无重叠的比较等）。

这层已经写进 `docs/HANDOVER.md`：**两个方向由两种机制分别覆盖，
别以为测试覆盖了全部**。凡是「让 A 服从 B」的测试都自带这个盲区。

验证：`pnpm check` 5 项全通过；`pnpm test` **429 项全绿**（36 个文件，+5）；
`pnpm build` 通过并部署。

## 轮次：同一件事的两条触发路径（自动 vs 手动）—— 顺手挖出一个死开关

上一轮的矿脉是「同一概念有几处实现」；这轮把它换成**「同一件事的两条触发路径」**：
自动同步已经有一句「已在同步则跳过」，而手动命令走的是另一个入口。

### 前半段：两个入口的守卫不对等 —— 但不是 bug

`SyncService` 的 `enqueue` 是串行队列（用**计数器**而不是布尔量做「在跑」的判据，
注释解释了为什么）。手动命令不做「已在同步则跳过」，于是连点会排几次队列 ——
只是多跑几遍，**不是正确性问题**，没动。

### 真问题：`sync.enabled` 是个死开关

设置页有「启用笔记同步」，`data.json` 里存着值，README 也列着它 ——
而 `src` 里**没有一处读它**（`grep '\.enabled'` 唯一命中的是 `installer.enabled`）。
于是用户关掉同步之后，自动提交照样每 N 分钟把笔记**推上远端**：
他做了 UI 提供给他的那个动作，却没有任何效果 —— 这比没有那个开关更糟。

对比：`installer.enabled` 是被读的（门控启动时的自动检查），所以边界照它定 ——
**只管后台自动动作，不拦命令面板里的显式命令**（那是用户当下主动的意图）。

修法：`AutomaticsSettings` 加 `enabled`，装配层注入；`automatics.start()` 里关掉时
直接返回（`stop()` 已清表且递增了世代号，所以正在跑的 fire 回来也不会重新起表）。
设置页每次改动都走 `commit()` → `applyDerivedSettings()` → `sync.reload()` →
`automatics.restart()`，所以拨开关**立刻生效**，不用重启。

### 同一文件里发现第二处：文案少了「并同步」三个字

`fire()` 里 `kind === "commit"` 调的是 `service.sync()`（提交 → 拉取 → 推送），
而设置页那一项写的是「自动提交间隔」+「设为 0 表示关闭」。
用户读到的意思于是变成「只提交」→ 会以为把「自动推送 / 自动拉取」设为 0
就能拦住网络动作 —— **拦不住**，推送与拉取随那条链路一起发生。

先确认行为是刻意的，不是实现错：那条映射**已被测试钉住**（`expect(calls).toEqual(["sync"])`），
且参考项目一致（obsidian-git 的定时器叫 `autoSaveInterval`，做的是 `commitAndSync`，
界面原文是 `Auto commit-and-sync interval (minutes)`）。
**所以错在文案**，改的是文案（zh-cn + en），并在代码里把「为什么不能改成 commitAll()」
写清楚（那样名字相符了，但「只在本地备份」的用户再也得不到推送）。

### 这轮最有价值的一段：补上一个测试与类型都覆盖不到的盲区

修完做四个方向变异，前三个都被抓住，**第四个抓不到**：

```
把 index.ts 的 enabled: deps.getSettings().sync.enabled 改成 enabled: true
  → 全量测试 12/12 全绿，tsc 也通过
```

因为测试直接给 `Automatics` 注入设置对象，**看不见装配层那一行**；
而类型上 `true` 也是 `boolean`。这个盲区正好是**这轮的 bug 本身**——
「设置项只被写、从没被读」和「接错线」是同一类问题。

项目已有「未使用的 i18n 键」自查（理由写着「死键是信号」），载体不同而已。
所以给 `scripts/checks.mjs` 加了第 6 项「设置项无人读取」。

判据收紧了三轮才可用（记录踩点，下次别重走）：

1. 第一版只匹配 `.字段` → `installer.enabled` 被判「无人读」（它读的是
   `const settings = host.getSettings().installer; if (!settings.enabled …)`）；
2. 加「提升访问」条款，但正则写成 `\.局部变量\.字段` —— **多写了一个 `\.`**，
   `!settings.enabled` 就匹配不到（前面是 `!` 不是 `.`）。改成 `(?<![\w.])名字\.字段`；
3. 又加过一条「文件名里含容器名就算」的兜底 —— 它会把 `automatics.ts` 算成读过
   `sync.enabled`（因为文件名里有 sync），**把检查彻底废掉**。删掉。

最终判据：只扫 `installer.*` / `sync.*`（顶层字段读起来形如 `this.settings.language`，
容器名与局部变量混在一起扫不准）；`settingsTab.ts` **不在范围内**（它读设置是为了渲染，
不是消费 —— 少了这条，每个字段都会被设置页自己「读」到）。

两条 `EXEMPT`（都是「settingsTab 组参数对象 → 消费方读参数属性」这个模式，
读取点在范围外、消费点拿到的是参数；`lastUpdateCheckAt` 还在参数里改了名）。
并在注释里写明**别为了消掉它们去放宽判据** —— 试过「属性名出现在参数类型里就算用过」，
后果是 `AutomaticsSettings.enabled` 会把 `sync.enabled` 也算成用过，检查就废了。

验证：把接线那行删掉、改成 `enabled: true`，自查都报错（退出码 1）并列出 `sync.enabled`。

### 测试

- `automatics.test.ts` +4：那一档**调的是 sync 而不是 commitAll**（守文案与实现的
  双向关系）、关掉时不起表、运行中关掉立刻停表、再打开能恢复（不会永久关死）。

**四个方向变异**：去掉总开关判断 → 3 条失败；条件取反 → 8 条失败；
改成 `commitAll()` → 5 条失败；改装配层写死 `true` → **测试全绿**（由新的自查兜住）。

验证：`pnpm check` **6 项**全通过；`pnpm test` **433 项全绿**（36 个文件，+4）；
`pnpm build` 通过并部署。
