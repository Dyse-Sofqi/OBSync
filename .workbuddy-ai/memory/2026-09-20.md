## 轮次：`pre-push` hook —— 把「忘了跑」也覆盖掉

用户追问：**「修完之后，这种情况以后还会出现吗？」**

上一轮我答过一半（「漏文件还会发生，但静默不会了」），**那一半是偷懒的**：
`pnpm verify:head` 是**工具**，不是**机制** —— 只有想起来跑才起作用。
用户真正在问的是第三层：**「不管也会被拦住吗？」** 而当时答案是「不会」。

### 三层要分开答

| 层 | 答案 |
| --- | --- |
| 漏 `git add` 本身 | **会** —— 手动暂存的固有风险，根除不了 |
| 漏了之后、本地能发现 | **会**，只要你跑 `verify:head`。但**依赖你记得** |
| 漏了之后、**不管也会被拦住** | 挂到 git 上才有 —— 这一轮补的就是它 |

### 选 pre-push，不是 pre-commit

- **commit 是本地历史，随时能 `git reset`**；**push 才是「别人能看到」的时刻**，
  也正是「HEAD 是红的」真正有害的时刻（别人克隆下来跑测试会看到失败）；
- push 频率远低于 commit，3 分钟等得起；
- pre-commit **根本检查不了这件事** —— 那个时刻你还不知道「该提交的都提交了没有」。

### 实现

- `.githooks/pre-push`：跑 `pnpm verify:head`，红了 `exit 1` 拦住 push。
  - **找不到 pnpm 时放行**而不是拦下：一个装不上工具的环境不该把人锁在仓库外面；
  - 打印「跳过本次检查：`git push --no-verify`」—— 逃生舱要在被拦住**之前**就告诉人。
- hook 放 `.githooks/` 而不是 `.git/hooks/`：后者不进版本控制，重新克隆就没了 ——
  而「防漏提交」恰恰需要它**一直在**。
- `pnpm hooks:install` = `git config core.hooksPath .githooks`。本机已启用。

### 验证（两条路径都实跑）

| 场景 | 结果 |
| --- | --- |
| `git hook run pre-push`（HEAD 绿） | 退出码 **0**，`Test Files 55 passed`，工作区被原样恢复 |
| 把 `if pnpm verify:head` 换成 `if false` | 退出码 **1** + 打印阻止信息 —— **红的时候真拦得住** |

第二条是必须的：只验「跑了」验不出「拦得住」，而后者才是 hook 的全部意义。

提交：`c04dd83`（`.githooks/pre-push` + `package.json` + README / HANDOVER 文档）。

### 一个反复出现的判断偏差

**「给了工具」不等于「解决了问题」。** 上一轮我加了 `verify:head` 就以为答完了 ——
但工具的价值取决于人想起来用它，而这次出问题的根源恰恰是「人会忘」。
**凡是「靠人记得」的防线，都要再问一句「忘了会怎样」。**

这个项目里已经有过同型的两次：

- `sync.enabled` 死开关 —— 设置页有开关、代码不读 → 用户以为关了，其实没关；
- `requestedVersion` 有字段没入口 —— 字段有效果、界面上改不了。

三次都是「某一层写了，另一层没接上」。**这次是「工具写了，触发点没接上」。**

## 轮次：发 0.1.2（归档 → 版本号 → CHANGELOG → README → 审核复查 → GitHub 发版）

用户一次性给了完整清单。按顺序做完，其中查出一个**真问题**（见下）。

### 做了什么

| 步骤 | 结果 |

| 版本号 → 0.1.2 | `manifest.json` / `package.json` / `versions.json` 三处同步（`versions.json` 的值是 **minAppVersion**，不是插件版本） |

| README 中英对等 | 英文 Features 落后好几处（「四个按钮同一行」「shows two rows」「source-control view」「reset — use with care」），逐条更新；补英文缺的 **Usage / Why another one / Notes on Gitee** 三节 |

| GitHub 发版 | `api-replay.mjs` 重放 20 个提交（**SHA 全一致**）→ Release `0.1.2` → 三件套（sha256 逐一比对一致） |

### 查出的真问题：`api-replay.mjs` 会误移标签

脚本第 147-149 行**硬编码**着：

```js
await api("PATCH", `/repos/${repo}/git/refs/tags/0.1.1`, { sha: parent, force: true });
```

注释写着「release API 建的那个 tag 指向被丢弃的合并提交」—— 那是**首推时的一次性修正**。
留在通用脚本里就成了定时炸弹：这次重放 20 个提交后，**本来正确的 `0.1.1` 标签被拖到了
`dd5e0f4`（0.1.2）**。症状很隐蔽 —— `git checkout 0.1.1` 会拿到 0.1.2 的代码，
而脚本自己报的是 `✔ 标签 0.1.1 → …`，看起来一切正常。

**修法**：删掉那三行，并把「标签不在这里碰」的理由写成注释。远端标签已用一条显式 PATCH
修回 `2f1ac07`（0.1.1 的发布提交）。

**教训**：临时脚本被正式化（进了 `scripts/`、写进 `RELEASE.md`）时，要把里面的
**一次性动作**挑出来 —— 它们对新场景往往是错的，而且**错得静默**（脚本还报 ✔）。

### Gitee 侧

`main` 与**标签都自动同步了**（实测：`0.1.2` 建完没多久 `git ls-remote gitee` 就能看到，
指向 `dd5e0f4`，与 GitHub 一致）—— 但 **release 与附件不会自动同步**，要手动建一次。

为此新增 `scripts/gitee-release.mjs`（`pnpm gitee:release <版本>`），把三个坑固化进去：

1. **Gitee 建 release 的接口没有 `files` 参数** —— 传了会被**静默忽略**（返回 201、
   release 建出来了、附件一个都没有）。附件是独立接口、**一次只能传一个**；
2. 本机**没有 `jq`**（`docs/RELEASE.md` 早先的手敲 curl 示例用了它，那一步会直接失败）；
3. **release body 从 `CHANGELOG.md` 抽该版本的段落** —— 单一事实来源，
   不用维护第二份文案。

脚本最后**核对附件数**，不等于 3 就非零退出 —— 防「看起来发完了、其实没附件」。

结果：release id `1154451`，三个附件（293566 / 290 / 24061 字节）全部到位；
**下载地址实测**（跟随重定向）字节数与本地逐一一致。

### 一个 Git Bash 的坑（顺带踩到）

校验下载时用 `curl -o /dev/null` → **exit 23（write error）+ 报 0 字节**，
看着像「下载不了」，其实文件是好的。Git Bash 下要用 `$TEMP` 里的临时文件。
（与文档里记过的「`esbuild --outfile=/dev/null` 会在仓库里建出 `dev/null`」同源。）
已写进 `docs/RELEASE.md`。

## 轮次：自身更新来源可指定（用户：「我直接指定该插件的镜像地址」）

先答了两个问题，答案都是「读代码得出的」：

1. **为什么自身更新不找镜像** —— `updateSelf` 里写着 `{ allowMirror: false }`，注释说明
   「自己更新必须来自官方仓库」。理由充分：镜像被伪造等于整个插件被替换（它能读笔记、
   能用令牌）。
2. **手动加进跟踪列表会怎样** —— **会重载自己**：`install()` 在 `wasEnabled` 时调
   `reloadPlugin`（disable → enable），而 `selfUpdate.ts` 开头那段注释警告的正是这件事。
   失败就停在「已禁用」，且 `community-plugins.json` 里记的是未启用，**重启也回不来**。

用户的诉求是「指定一次、以后不用找」。于是加了显式入口
（`settings.installer.selfUpdateSource` + `resolveSelfRepo()` + 设置页输入框）。

**关键的论证**：用户本来就能通过「添加插件仓库」做到同样的事，而且那条路**更危险**
（会重载自己）。所以给一个显式入口是在**降低**风险，不是增加。

### 踩到的坑（被自己写的测试抓到）

第一版：`fetchItem(PLUGIN_SPEC, formatRepoId(source), …)`。

**`formatRepoId` 只返回 `owner/repo`，不带 host** —— 于是 `sofqi/OBSync` 被
`resolveRepo` 按默认 host（github）重新解析，**用户填的 Gitee 地址悄悄失效**，
而界面看起来一切正常。修法：`{ allowMirror: false, defaultHost: source.host }`。

那条用例断言「有请求打到 gitee」**且**「**没有**请求打到官方仓库」——
**后者是关键**：只断言前者的话，一个「两边都请求一遍」的实现也能通过。

**又一次印证：先写测试，再让它告诉我哪里错了。** 这次是测试直接抓出了实现里的 bug，
而不是事后补测试。

新增 7 条用例（838 → 845）。

**Gitee 下载实测**：三个文件字节数与本地相同（295232 / 290 / 24061）。

### 一个观察（免得下次误判）

Gitee 建 release 时创建的是 **annotated tag**：`git ls-remote gitee` 里能看到两条 ——
`refs/tags/0.1.3` 是 tag 对象（`5963fb2`），`refs/tags/0.1.3^{}` 才解引用到提交（`9aa55e5`）。
GitHub 那边是 lightweight，直接指向提交。

**两者等价**（`git checkout 0.1.3` 在两边拿到同一份代码）。所以看到「两端 tag SHA 不同」
时不必惊慌，先看有没有 `^{}` 那一行。

`scripts/gitee-release.mjs` 一次跑通、没出任何问题 —— 上一轮把三个坑（`files` 参数被忽略、
附件一次一个、没有 jq）固化进脚本是值的。

### 两个下次会再撞上的点

**① 本机没有 `pwsh`，跑的是 Windows PowerShell 5.1。** `Get-Content -Raw` 按 ANSI 读文件，
UTF-8 的中文正文直接变乱码；更坑的是 `ConvertTo-Json` 会把 `Get-Content` 返回的字符串
**连同 `PSPath`/`PSDrive`/`PSProvider` 一大坨属性**一起序列化 —— 生成出来的
`release.json` 有 34 KB（正常 1.6 KB），`gh api --input` 必然解析失败。
读中文文件一律走 `[System.IO.File]::ReadAllText($p, [Text.Encoding]::UTF8)`，
写回去用 `UTF8Encoding($false)`。

**② Gitee 凭据本机**没有**存。** 凭据管理器里只有 GitHub（`git:https://github.com`），
`git credential fill` 对 gitee.com 直接 `Cannot prompt because user interactivity has been
disabled`。这次是让用户把 PAT 贴进对话解决的；下次发版同样要现给，别指望能自动取到。

**顺带发现（与本次发版无关）**：GCM 打了 `TLS certificate verification has been disabled`
警告，是机器级配置。值得单独确认是不是有意的。
